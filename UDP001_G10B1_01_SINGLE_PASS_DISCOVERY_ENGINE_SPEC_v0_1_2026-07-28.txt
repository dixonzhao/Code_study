1. PURPOSE AND ARCHITECTURE DECISION
======================================================================

G10B0 selected:

P2 = FOUNDATION_BASED_NEW_STREAMING_ENGINE

Reason:

- the Foundation exposes all eight required public primitives;
- Gate 2 remains file/CLI-oriented;
- Gates 3-5 expose reusable chunk APIs, but composing all accepted Gate files
  would still require unsuitable global intermediate files;
- running the existing path independently for 23 discovery batches would scan
  the approximately 800 MB Raw CAN source 23 times;
- materializing all signals globally would create three large long-stream
  intermediates.

G10B1 must therefore implement one bounded-memory Raw CAN scan that:

1. loads the accepted G10A2 AUTO_DISCOVERY configuration;
2. decodes the authoritative FrameCount and 705 discovery candidates;
3. routes every candidate update to exactly one deterministic BatchId;
4. preserves real updates in batch-partitioned long form;
5. creates one bounded-width FrameCount shard per batch;
6. preserves missingness, validity and source-order provenance;
7. never creates a 705-signal wide table;
8. never rescans Raw CAN once per batch;
9. does not perform statistical relevance screening.

This is U001 data preparation.  U002 remains the owner of correlation,
baseline, residual, anomaly, lag and variable ranking.

6. SINGLE-PASS SOURCE READING
======================================================================

--run repeats the preflight checks and then reads Raw CAN exactly once with
pandas chunks.

Use:

- exact detected encoding;
- exact detected delimiter;
- exact detected header row;
- usecols limited to required Raw byte columns and optional DateTime/Time[us]
  provenance fields;
- globally monotonic zero-based SourceRowIndex after the detected header;
- exact max-source-rows stopping when configured.

Do not sort Raw rows.  Do not use DataFrame index labels as SourceRowIndex.
Do not read Raw CAN separately for each BatchId.

Decode Foundation/DBC definitions once outside the source-chunk loop.

Performance rules:

- create vectorized present/complete/byte-valid masks per message group where
  practical;
- decode only DECODED_UPDATE message rows;
- buffer batch output records per source chunk and append them in blocks;
- never append one CSV row through a separate pandas write call;
- keep at most the current source chunk, bounded output buffers and one open
  FrameCount aggregation state in memory;
- stateful FrameCount processing and frame finalization must remain serial;
- do not add multiprocessing in v0.1.

======================================================================
7. MESSAGE UPDATE AND DECODE SEMANTICS
======================================================================

For each required message group and source row:

NO_UPDATE:

- all required byte cells blank/NaN;
- emit no update.

INCOMPLETE_MESSAGE:

- some but not all required byte cells present;
- emit no decoded update;
- count and retain at most 20 SourceRowIndex examples globally.

INVALID_BYTE:

- all required cells present but one or more are not integer bytes 0-255;
- emit no decoded update;
- count and retain at most 20 examples.

DECODED_UPDATE:

- all required bytes present and valid;
- decode only configured FrameCount/candidate signals for that message;
- emit one real update per configured signal;
- preserve raw zero, signed RawCode, PhysicalValue and known enum label.

Never forward-fill bytes or measurements.  Never replace blank with zero.

Deterministic update order:

1. SourceRowIndex;
2. MessagePlanOrdinal;
3. accepted DBC signal order;
4. CanonicalName as a final deterministic tie-breaker.

======================================================================
8. FRAMECOUNT ASSIGNMENT AND STREAMING FRAME STATE
======================================================================

The exact configured FrameCount CanonicalName is the only authoritative frame
observation.

For each observation:

- PhysicalValue must be numeric, finite and exactly integer-valued;
- equal repeated observations are allowed;
- a decrease/reset/wrap is blocking;
- conflicting observations at one SourceRowIndex are blocking.

Assignment semantics equal accepted Gate 3:

- same SourceRowIndex -> FRAME_EXACT, age 0;
- later row within limit -> FRAME_ASSIGNED, age=current row-last frame row;
- no prior -> FRAME_UNASSIGNED_NO_PRIOR;
- beyond limit -> FRAME_UNASSIGNED_LIMIT;
- unassigned updates remain in long update shards but never enter frame views.

When a newly observed FrameCount differs from the open FrameCount:

1. finalize the previous frame for every batch;
2. write exactly one row for that frame to every batch frame shard;
3. reset only the open-frame aggregation state;
4. process same-row candidate updates under the new FrameCount.

Repeated equal FrameCount observations do not finalize a frame.

At end of source, finalize the last open frame exactly once.

Every batch frame shard must contain the same strict increasing FrameCount
sequence, including frames with no candidate update in that batch.

======================================================================
9. TYPE, VALIDITY, AGGREGATION AND HOLD
======================================================================

Apply accepted G4 type semantics from the G10A2 signal policy.

- FLOAT: finite numeric PhysicalValue;
- INTEGER: numeric and exactly integer-valued;
- BOOLEAN: exactly 0 or 1; zero is valid false;
- ENUM: integer RawCode; unknown label remains valid with
  MissingReason=UNKNOWN_ENUM_CODE;
- BITFIELD: nonnegative integer RawCode; zero is valid.

Discovery ValidityRule must be NONE.  Type-consistent updates use Valid=1 and
MissingReason=VALID_UPDATE.  Type failures remain in the long stream with
Valid=0 and MissingReason=SOURCE_MISSING.

Within-frame policies:

- LAST_UPDATE: preserve the last real update, even when invalid;
- FIRST_UPDATE: preserve the first real update;
- ANY_TRUE: aggregate valid BOOLEAN updates only;
- BITWISE_OR: OR valid nonnegative integer updates;
- COUNT_UPDATES: output real update count;
- KEEP_STREAM_ONLY: no frame columns.

G10A2 discovery HoldPolicy is NONE.  No cross-frame hold is applied.  When a
signal has no update in a frame:

- value and label blank;
- updated=0;
- update_count=0;
- age blank;
- valid=0;
- missing_reason=NO_UPDATE.

Do not infer 327.66, 273.15 or zero as invalid in G10B1.

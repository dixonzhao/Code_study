U002 ALGORITHM CARD中文说明书

版本：1.0
日期：2026-08-03
Owner：Zhao Zhili
适用对象：算法设计者、Module开发者、实验执行者、Reviewer和后续接手人员


一、读完后应该会什么

读完后，你应该能够：

1. 用一句话解释Algorithm Card是什么；
2. 区分Algorithm Card、Module Manifest、Artifact Manifest和Run Manifest；
3. 判断一个统计方法是否已经被项目真正“拥有”；
4. 从工程问题写出明确的数学定义、输入、输出和假设；
5. 判断某个方法什么时候能用、什么时候必须停止使用；
6. 为算法设计最小可验证Experiment；
7. 把Experiment结果连接到Keep / Reject / Modify和AlgorithmStatus；
8. 向上长、新成员或外部开发者解释为什么程序中存在这个方法。


二、一句话定义

Algorithm Card是一份人类可读的“算法设计说明、适用边界、验证计划和批准状态记录”。

它回答的不是：

  代码怎样写？

而是：

  为什么需要这个方法？
  它数学上究竟做什么？
  它依赖哪些假设？
  它能支持什么结论？
  它怎样被验证后才能进入正式Pipeline？

可以把它理解为算法的：

  出生证明
  + 使用说明
  + 风险说明
  + 实验计划
  + 批准履历


三、为什么本项目必须有Algorithm Card

本项目早期已经发生过一种典型风险：

  看到Correlation
      ↓
  增加Spearman
      ↓
  增加Mutual Information
      ↓
  增加Conditional Baseline
      ↓
  增加Stage 2
      ↓
  增加Lag Scan、Evidence Score和Event Hint

每一步单独看都可能合理，但如果没有稳定的算法设计记录，就会出现：

- 不知道它最初解决什么问题；
- 不知道为什么不用更简单的方法；
- 不知道数学方向和单位；
- 不知道默认参数从哪里来；
- 不知道它依赖什么数据假设；
- 不知道结果能否复现；
- 不知道它是探索性方法还是正式方法；
- 不知道什么时候应该停用；
- 程序实现逐渐代替工程判断。

Algorithm Card的核心目的就是恢复Algorithm Ownership：

> 算法进入程序之前，项目必须先拥有它的定义、理由、边界和验证方法。


四、它在U002架构中的位置

U002固定Stage：

  S0 Intake and Contract Gate
  S1 Semantic Reconstruction and Analysis Preprocessing
  S2 Analysis View and Population Construction
  S3 Primary Outcome Construction
  S4 Baseline and Residual
  S5 Evidence Engines
  S6 Candidate Synthesis
  S7 Handoff and Export

Algorithm Card位于“需求与数学设计层”，Module位于“工程实现层”。

推荐关系：

  工程问题
      ↓
  Algorithm Card
      定义目的、数学、假设和验证
      ↓
  Experiment设计
      ↓
  Module实现
      ↓
  Module Manifest
      定义机器接口、身份和执行策略
      ↓
  Run + Artifact证据
      ↓
  Decision Log
      ↓
  AlgorithmStatus更新

因此Algorithm Card不是Module代码写完后补的装饰文档，而是Module正式开发前的设计输入。


五、它与三个Manifest分别有什么区别

1. Algorithm Card

回答：

  为什么采用该方法？
  数学定义是什么？
  假设与局限是什么？
  如何验证？


2. Module Manifest

回答：

  哪个Module实现该能力？
  它位于哪个Stage？
  需要什么输入？
  提供什么Artifact？
  怎样执行和SelfTest？


3. Artifact Manifest

回答：

  某一份实际结果由谁生成？
  来自哪些Parent？
  覆盖什么范围？
  Payload在哪里？


4. Run Manifest

回答：

  本次运行实际选择了哪些Module、Profile和配置？
  S0–S7怎样执行？
  最后产生了哪些Artifact？


一句话关系：

  Algorithm Card定义“为什么和怎么算”
  Module Manifest定义“谁按照什么接口实现”
  Artifact Manifest记录“这次实际生成了什么”
  Run Manifest记录“整次实际怎样运行”


六、当前U20A能自动检查什么，不能检查什么

当前U20A Core Contract中：

- Module Manifest含有AlgorithmStatus；
- Module Pack要求包含Algorithm Card或Reference；
- U20A Validator会检查Manifest字段和AlgorithmStatus枚举；
- U20A Validator不会阅读自然语言并判断数学内容是否正确；
- Algorithm Card目前不是U002 Core Contract v0.1中的第四种机器Manifest。

因此必须区分：

  结构通过
    文件、字段和引用符合规则。

  算法批准
    数学定义、实验和Decision已经完成。

一个Module即使SelfTest通过，也不代表算法自动成为FORMAL。

未来可以为Algorithm Card增加机器索引或Schema，但不应在MVP阶段为了文档自动化推迟Golden Run。


七、什么时候必须创建Algorithm Card

以下任一情况出现，就必须有Algorithm Card：

1. 定义或改变PrimaryOutcome；
2. 定义Baseline或Residual；
3. 计算Anomaly或Evidence Score；
4. 使用统计阈值；
5. 定义Candidate合成、排序、合并或数量上限；
6. 根据多个信号推断一个语义对象；
7. 处理Lag、Memory、AR、ARX或Prediction Error；
8. 使用机器学习或数据驱动模型；
9. 新方法会影响工程结论；
10. 方法的参数不是纯显示设置，而会改变分析结果。

以下简单动作通常不需要独立Algorithm Card：

- 文件复制；
- CSV导出；
- GUI按钮布局；
- 路径选择；
- 不改变数据语义的格式转换；
- 已在上层Card中明确覆盖的简单确定性辅助函数。

判断标准：

> 如果改变它可能改变工程结论，就需要Algorithm Card或明确被哪张Card覆盖。


八、一张Card对应一个Module吗

不一定严格一对一。

常见关系：

1. 一张Card对应一个Module

适合独立算法，例如：

  Global Robust Location Baseline
  Robust Residual Magnitude Evidence


2. 一张Card由多个Module实现

同一算法可能有：

- Python实现；
- MATLAB验证实现；
- Batch实现；
- GUI包装实现。

它们可以引用同一张Algorithm Card，但各自拥有不同Module Manifest。


3. 一个Module引用多张Card

如果Module组合多个有独立假设和验证要求的方法，可以引用多张Card。

但要警惕：

> 如果一个Module需要十几张Card，可能说明Module职责过大，应该拆分。


4. 简单辅助算法归入主Card

例如中位数计算内部的排序和NaN过滤，不必为每个函数单独建卡，只需在主Card中说明规则。


九、AlgorithmStatus的真实含义

Module Manifest允许：

  EXPERIMENTAL
  PROVISIONAL
  FORMAL
  DEPRECATED


1. EXPERIMENTAL

含义：

- 正在探索；
- 数学或参数仍可能明显改变；
- 只能用于Experiment；
- 不应默认进入正式交付Pipeline。


2. PROVISIONAL

含义：

- 目的、数学和边界已经明确；
- 有基本SelfTest或初步真实数据证据；
- 可以用于受限调查；
- 仍有未完成验证；
- 输出必须带限制说明。

当前Camera Target Selector适合标为PROVISIONAL，因为它能支持调查，但还不能宣称完全恢复真实AKBPTS选择对象。


3. FORMAL

含义：

- Algorithm Card完整；
- 实现与数学定义一致；
- 必需SelfTest和Experiment完成；
- Acceptance指标满足；
- Decision Log明确批准；
- 适用范围和限制已记录。

FORMAL不等于永远正确，也不等于适用于所有车型和所有数据。


4. DEPRECATED

含义：

- 不再推荐新Run使用；
- 为历史复现可能暂时保留；
- 必须说明替代方法和迁移条件；
- 不能悄悄删除导致旧Run不可解释。


十、写Card之前先回答四个门槛问题

任何新算法在进入正式设计前，先回答：

1. 它解决什么具体问题？
2. 为什么现有方法不足？
3. 是否存在更简单、可解释的方法？
4. 怎样通过数据或实验判断它有效？

如果四个问题无法回答，先不要写代码。

这不是阻止创新，而是避免程序继续无边界膨胀。


十一、Algorithm Card的标准结构

一张正式Card至少包含以下十五部分。


SECTION AC1：身份

字段：

  CardId
  CardVersion
  AlgorithmName
  AlgorithmStatus
  Owner
  CreatedDate
  LastUpdatedDate
  RelatedStage
  RelatedModuleIds

推荐CardId：

  AC_U002_<Stage>_<FunctionalName>

示例：

  AC_U002_S4_GLOBAL_ROBUST_LOCATION_BASELINE

CardVersion是文档和算法定义版本，不等于ModuleVersion。


SECTION AC2：一句话目的

必须能用一句话说明：

  该算法把什么输入转成什么输出，以解决什么工程问题。

不合格：

  使用统计方法分析误差。

合格：

  在声明的BaselineFitPopulation上估计Camera–Radar PrimaryOutcome的稳健常态中心，并生成可追溯的BaselinePrediction供Residual计算。


SECTION AC3：问题背景与不使用它的后果

说明：

- 数据中观察到什么结构；
- 为什么直接Threshold不够；
- 不处理会产生什么误报或解释错误；
- 当前业务为什么需要解决。

这里只写已知背景，不把Hypothesis写成事实。


SECTION AC4：架构位置与职责边界

必须说明：

- 位于S0–S7哪个Stage；
- 上游Artifact是什么；
- 下游谁会使用结果；
- 它明确不负责什么。

示例：

  S4 Baseline只估计常态位置并产生Residual。
  它不负责判断Camera或Radar谁错。
  它不负责生成最终Review Case。


SECTION AC5：输入与数据资格

逐项定义：

- 输入字段或Artifact；
- 数据类型；
- 单位；
- ClockDomain；
- Frame范围；
- Validity要求；
- Missing行为；
- SignalAge限制；
- 最小样本数；
- 是否允许Forward-filled数据；
- TUNING与EVALUATION Population。

不要只写：

  输入DataFrame。

应写：

  PrimaryOutcome：numeric，单位m，FrameCount域；
  Eligibility：boolean；
  只使用Eligibility=true且非缺失样本；
  BaselineFitPopulation由冻结的Run配置声明。


SECTION AC6：精确数学定义

这是Card核心。

至少说明：

- 符号；
- 方向；
- 单位；
- 公式；
- 条件集合；
- 边界行为；
- 零分母或空集合处理；
- 是否逐Frame、逐Window或逐Case计算。

示例：

  设D_t为PrimaryOutcome。

  B = median({D_t | t属于BaselineFitPopulation且Eligibility_t=true})

  BaselinePrediction_t = B

  Residual_t = D_t - B

必须进一步说明：

- 空集合时失败，不返回0；
- 输入单位为m，则B和Residual单位均为m；
- median只在声明Population上拟合；
- EVALUATION时不得根据结果重新调整B。


SECTION AC7：输出与语义

逐项定义：

- 输出名称；
- 数据类型；
- 单位；
- 正负方向；
- 有效范围；
- Status和Reason；
- 对下游允许支持的结论。

例如Residual必须明确：

  Residual不是Camera真实误差。
  它是剥离当前Baseline后的Camera–Radar discrepancy剩余量。


SECTION AC8：参数与配置

每个参数说明：

  ParameterName
  DefaultValue
  Unit
  AllowedRange
  Meaning
  TuningAuthority
  FrozenForEvaluation
  FailureBehavior

参数分三类：

1. Contract参数
   改变数据或数学语义，必须严格版本控制。

2. Tuning参数
   可在TUNING阶段选择，EVALUATION前冻结。

3. Display参数
   只影响显示，不改变结果。

不要把阈值写死在Python源码中而不进入配置和Card。


SECTION AC9：假设

明确列出算法成立需要什么。

示例：

- BaselineFitPopulation以正常或常态样本为主；
- PrimaryOutcome方向和单位稳定；
- Target association已达到声明的Eligibility；
- FrameCount域已对齐；
- Missing不会被伪装成真实0；
- 用于拟合和评价的Population边界明确。

假设不是免责声明，而是使用门槛。


SECTION AC10：失效模式与保护措施

每个算法至少回答：

- 输入缺失时怎样；
- 样本不足时怎样；
- 数据常数化时怎样；
- 极端值过多时怎样；
- 时间轴错误时怎样；
- 目标关联错误时怎样；
- 参数越界时怎样；
- 计算失败时输出什么Status和Reason。

推荐表述：

  FailureMode
  Detection
  SystemResponse
  DownstreamImpact

原则：

> 不确定时输出无资格或失败状态，不制造看似正常的数值。


SECTION AC11：为什么不用更简单或其他方法

必须记录至少一个替代方案。

示例：

  Mean
    对极端值敏感，因此第一版不用。

  Conditional Distance Baseline
    复杂度更高，当前Golden Run先验证Global Median；作为后续Experiment，不提前固化。

  LOESS / Huber Regression
    未来在Global Baseline无法消除稳定距离结构时再比较。

这部分防止“因为知道一个高级方法，所以就塞进去”。


SECTION AC12：验证计划

必须把验证拆成不同层次：

1. Synthetic SelfTest

用人工构造的小数据验证公式和边界。

2. Implementation Equivalence

用简单手算或独立实现确认代码与数学一致。

3. Smoke Run

在短真实范围验证接口、运行和Artifact。

4. TUNING Run

查看分布、确定可调参数和Candidate Policy。

5. EVALUATION Run

冻结参数后在声明的非重叠Population上评价。

6. Cross-Case Validation

条件允许时在其他视频或日志检查稳定性。


SECTION AC13：评价指标与Acceptance标准

指标必须直接对应算法目的。

例如Baseline可以考虑：

- Fit Population count；
- Median residual；
- Residual Q95；
- Residual与距离的剩余结构；
- Candidate rate；
- 对已知调查窗口的保留；
- 跨时间块稳定性。

但不能只看一个指标。

例如Candidate rate下降可能来自：

- 误报减少；
- 真异常被Baseline吸收；
- Eligibility过度收缩。

因此Acceptance必须同时检查数据覆盖、结构和人工复核。


SECTION AC14：结论边界与禁止表述

明确说明算法可以支持什么、不可以支持什么。

当前项目常见禁止表述：

- 没有Ground Truth时，不把discrepancy称为Camera真实误差；
- Association只代表统计或条件关系，不自动代表因果；
- Event Hint不等于已确认Event；
- Robust Rarity不等于物理严重程度；
- Prediction Error异常不自动等于传感器故障；
- Candidate排序不等于Root Cause排序。


SECTION AC15：实现、实验与决策链接

记录：

  RelatedModuleIds
  ModuleVersion
  ConfigurationSchemaId
  OutputArtifactTypes
  SelfTestIds
  ExperimentIds
  DecisionIds
  KnownLimitations
  ChangeHistory
  ReevaluationConditions

这部分把数学设计连接到实际软件和项目治理。


十二、Algorithm Card完整生命周期

STEP L1：问题被正式提出

输入来自：

- Known Fact；
- Observation；
- 业务要求；
- 已确认Design Gap；
- 某个Experiment失败结果。


STEP L2：创建EXPERIMENTAL Card

先完成：

- 一句话目的；
- 数学定义草案；
- 输入输出；
- 假设；
- 最小验证方法。

此时不能直接进入正式Pipeline。


STEP L3：审查复杂度

回答：

- 现有方法哪里不够；
- 有没有更简单方法；
- 新复杂度是否值得；
- 如何知道它真正改善。


STEP L4：设计Synthetic SelfTest

至少覆盖：

- 正常例；
- 边界例；
- 缺失例；
- 无效例；
- 参数异常例；
- 预期失败例。


STEP L5：实现Module

实现工具按照Card和接口实现，不自行改变数学定义。

如果实现中发现Card不完整，应返回Design Gap，而不是在代码中自行猜测。


STEP L6：运行Experiment

Experiment必须记录：

  目的
  输入
  方法
  唯一改变项
  输出
  结果
  结论
  Keep / Reject / Modify


STEP L7：PROVISIONAL使用

初步通过后可以在声明范围用于调查，但输出必须保留：

- AlgorithmStatus；
- Eligibility；
- Known Limitation；
- 人工复核要求。


STEP L8：Decision审批

只有Decision Log明确批准后，AlgorithmStatus才能升级为FORMAL。

Decision至少说明：

- 决定内容；
- 理由；
- 使用的Experiment证据；
- 被放弃或延期的方法；
- 重新评估条件。


STEP L9：版本化维护

如果改变以下任一项，需要评估Card版本：

- 数学公式；
- 输入资格；
- 输出语义；
- 阈值；
- Population定义；
- Failure behavior；
- Acceptance标准。

仅修改错字可以更新文档Revision，不一定改变算法主版本。


STEP L10：Deprecated但保持历史可追溯

废弃时说明：

- 为什么废弃；
- 最后适用版本；
- 替代Card；
- 旧Run怎样复现；
- 新Run禁止使用的日期或Engine版本。


十三、怎样阅读一张Algorithm Card

第一次不要从第一行逐字读到最后。采用五遍阅读法。

第一遍：30秒看目的

只看：

  AlgorithmName
  Status
  Stage
  One-Sentence Purpose

回答：

  它为什么存在？


第二遍：2分钟看数学

只看：

  Inputs
  Formula
  Outputs
  Units
  Direction

回答：

  它实际算了什么？


第三遍：2分钟看风险

只看：

  Assumptions
  Failure Modes
  Claim Boundary

回答：

  什么时候不能相信？


第四遍：2分钟看证据

只看：

  Experiment
  Metrics
  Acceptance
  Decision

回答：

  为什么目前是这个Status？


第五遍：2分钟看落地

只看：

  RelatedModule
  Configuration
  Artifact
  SelfTest

回答：

  在软件里对应哪里？

这样一张Card通常十分钟内可以建立整体概念。


十四、教学示例：Global Robust Location Baseline

以下只是说明Card怎样写，不等同于完成正式批准。


AC1 身份

  CardId：AC_U002_S4_GLOBAL_ROBUST_LOCATION_BASELINE
  Version：0.1.0
  Status：PROVISIONAL
  Stage：S4


AC2 一句话目的

在声明的BaselineFitPopulation上估计PrimaryOutcome的稳健常态中心，生成BaselinePrediction和Residual，为后续Evidence提供不含整体位置偏移的分析量。


AC3 问题

Camera–Radar PrimaryOutcome可能存在约数米的稳定中心偏移。若直接对原始discrepancy做Threshold，大量常态偏移可能被误报为异常。


AC4 职责边界

负责：

- 估计全局稳健中心；
- 生成BaselinePrediction；
- 生成Residual。

不负责：

- 判断Camera或Radar谁错；
- 建立distance-dependent conditional baseline；
- 生成最终Candidate；
- 解释Root Cause。


AC5 输入

  PrimaryOutcome_t：numeric，单位m；
  Eligibility_t：boolean；
  BaselineFitPopulation：由Run配置冻结；
  ClockDomain：FrameCount；
  Missing和无资格样本不进入拟合。


AC6 数学

设合格集合为：

  F = {t | t属于BaselineFitPopulation且Eligibility_t=true}

全局Baseline：

  B = median({PrimaryOutcome_t | t属于F})

对可评价样本：

  BaselinePrediction_t = B

  Residual_t = PrimaryOutcome_t - B

如果F为空或不足最小样本数：

  不返回B = 0
  输出FAILED或INELIGIBLE状态


AC7 输出

  BaselinePrediction：m
  SignedResidual：m
  AbsoluteResidual：m
  BaselineStatus
  BaselineReason
  FitPopulationCount


AC8 参数

  MinimumFitCount
    必须在TUNING前定义；EVALUATION冻结。

当前没有distance bin参数，因为conditional baseline不属于本Card。


AC9 假设

- Fit Population的大多数样本代表常态中心；
- PrimaryOutcome方向和单位稳定；
- Target选择与Radar有效性已完成；
- FrameCount已对齐；
- 异常不会占据Fit Population的大部分。


AC10 失效模式

  样本不足
    -> BaselineStatus = INSUFFICIENT_DATA

  输入全缺失
    -> FAILED，不补0

  Fit Population被异常主导
    -> median可能吸收异常，需时间块和视频复核

  Distance结构仍明显
    -> 记录Observation，后续Experiment比较conditional baseline


AC11 替代方法

  Mean
    更简单但对极端值敏感。

  Conditional Median
    可处理distance-dependent结构，但更复杂且可能吸收真实异常，Golden Run第一版暂缓。

  Huber / LOESS
    在Global Median验证不足后再实验。


AC12 验证

  Synthetic：已知中心加少量极端值，检查median和Residual；
  Smoke：短Frame范围确认Artifact和单位；
  TUNING：检查分布与MinimumFitCount；
  Evaluation：冻结B后用于独立时间块；
  Review：确认已知异常没有全部被吸收。


AC13 Acceptance

- Fit count满足要求；
- Baseline Artifact完整；
- 合格Fit Population的Residual median接近0；
- 不通过扩大无资格区间人为降低Candidate；
- 已知调查窗口仍保留；
- 不出现Missing-to-zero fabrication。


AC14 结论边界

Residual只表示剥离当前全局中心后的discrepancy，不是Camera真实误差，也不是Root Cause。


AC15 链接

  RelatedModule：U002.S4.GlobalRobustLocationBaseline
  OutputArtifacts：BASELINE_MODEL / RESIDUAL_SERIES
  Experiment：待创建
  Decision：待创建

因此Status仍为PROVISIONAL。

十六、常见错误

错误1：把代码注释当Algorithm Card

代码注释解释实现细节，不能完整承担工程目的、假设、Experiment和Decision。


错误2：只写公式，不写数据资格

同一个公式在无效值、错Target或错ClockDomain下仍会给出数字，但没有工程意义。


错误3：只写优点，不写什么时候失败

这会把Card写成宣传材料，而不是工程控制文件。


错误4：参数只有默认值，没有来源

例如Threshold = 3.0，但不知道是3 m、3个MAD还是任意经验值。


错误5：看到结果后反复改参数，却仍称为Evaluation

这属于TUNING。修改后必须创建新Experiment和新Evaluation Run。


错误6：AlgorithmStatus由代码是否运行决定

程序运行成功只证明实现路径可执行，不证明算法有效。


错误7：只看Correlation就写“影响因素”

Association不等于因果。Card必须限制结论语言并设计稳定性和混杂检查。


错误8：复杂方法没有简单Baseline比较

如果ARX、MI或机器学习不能明显优于简单方法，就不值得进入正式Pipeline。


错误9：一张Card包含整个Analyzer

会把PrimaryOutcome、Baseline、Evidence和Candidate重新混在一起，破坏S0–S7职责。


错误10：Card与Module实现不同步

公式或参数改变后未更新Card、ModuleVersion和Experiment，导致文档失真。


错误11：没有Ground Truth却写Sensor Error

当前应使用Camera–Radar Discrepancy、Residual和Candidate等限定术语。


错误12：Card写得太长但找不到一句话目的

详细不等于清楚。第一页必须先让人知道它为什么存在。

十八、怎样用Algorithm Card学习算法

对于当前从物理和第一性原理转向ADAS算法工程的学习路线，Card也可以作为学习框架。

学习一个新方法时，不要只问：

  公式怎么推？

同时问：

1. 它解决的工程问题是什么？
2. 变量有什么物理意义和单位？
3. 公式从哪些假设出发？
4. 哪些项是模型结构，哪些项是估计参数？
5. 数据不满足假设时会出现什么残差？
6. 用什么实验区分模型不足和实现错误？
7. 它最终位于U002哪个Stage？

例如学习ARX时，未来Card会迫使我们同时明确：

- 输入u(t)和输出y(t)是什么；
- sample interval是多少；
- delay nk怎样定义；
- na、nb怎样选择；
- estimation与validation数据怎样分离；
- prediction error怎样解释；
- residual whiteness检查什么；
- Forward fill是否制造虚假memory；
- 模型只用于Candidate Evidence还是可解释Gain。

这样推导不会脱离真实工程。


十九、十分钟自检练习

选择一个熟悉的方法，例如Pearson Correlation。

不写代码，回答：

1. 一句话目的是什么？
2. 输入和输出是什么？
3. 它只衡量什么关系？
4. 非线性、异常值和自相关会怎样影响它？
5. p-value能否代表工程重要性？
6. 多看700个变量时怎样控制假阳性？
7. 怎样做时间块稳定性检查？
8. 它应位于S5 Evidence还是其他Stage？
9. 它能否直接生成Root Cause结论？
10. 哪个Experiment能决定是否保留？

如果这些问题回答不清楚，就说明“会调用corr函数”还不等于拥有该算法。


二十、维护者检查清单

开发前：

- 一句话目的明确；
- 架构Stage明确；
- 输入、单位、方向和ClockDomain明确；
- 数学公式明确；
- 简单替代方法已比较；
- 不支持的结论已写明。

实现前：

- AlgorithmStatus不是FORMAL冒充；
- 参数进入Configuration Schema；
- SelfTest覆盖边界和失败；
- 输出Artifact和Status/Reason明确；
- Module职责没有越过Stage边界。

实验后：

- Run和Artifact证据可追溯；
- 指标没有只挑有利结果；
- TUNING与EVALUATION区分；
- Known Limitation更新；
- Keep / Reject / Modify明确；
- AlgorithmStatus只通过Decision更新。

1. Algorithm Card说明算法为什么存在、数学上怎么算、什么时候可信。

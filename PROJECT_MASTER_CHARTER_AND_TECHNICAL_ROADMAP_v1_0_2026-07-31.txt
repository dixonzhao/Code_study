0. READ THIS FIRST
======================================================================

This project converts a large, difficult-to-review vehicle-test dataset into a
small number of traceable engineering investigation candidates.

The project is not intended to automatically declare which sensor is wrong or
to produce an unreviewed root-cause verdict. Its first responsibility is:

  large CAN and video dataset
  -> trustworthy FrameCount-domain data
  -> Camera-Radar discrepancy and residual evidence
  -> ranked anomaly windows
  -> synchronized video/CAN review
  -> reproducible engineering disposition

The governed product architecture has three programs:

  U001  Data Preparation Workbench
        Raw CAN + DBC -> traceable analysis data

  U002  Analysis Workbench
        Prepared data -> discrepancy, residual and investigation candidates

  U003  Evidence Review Workbench
        Candidate windows -> synchronized human review and evidence export

Current product status:

  U001 Portable v0.2
    COMPLETE / RELEASE ACCEPTED / BASELINE FROZEN

  U002 Analysis Workbench
    NEXT ACTIVE DEVELOPMENT PROGRAM

  U003 Evidence Review Workbench MVP v0.1
    COMPLETE / RELEASE ACCEPTED / BASELINE FROZEN

The immediate project objective is one traceable Golden Run through all three
programs. U002 is the missing middle layer.

This document explains the whole project. It does not replace the frozen
Unified Data Contract, interface manuals, Algorithm Cards, Experiment Log,
Decision Log or product-specific acceptance evidence. Where a detailed
contract conflicts with this overview, the more specific approved contract
controls.

======================================================================
1. PROJECT ORIGIN AND ENGINEERING NEED
======================================================================

The original assignment was a manual Camera-versus-Radar vehicle-test review:
inspect approximately one and a half hours of Stereo Camera video together
with CAN data, identify suspicious behavior, capture relevant evidence and
summarize where each sensing system appears stable or problematic.

The original request did not provide:

- a formal anomaly definition;
- reliable ground truth;
- an approved target-association rule;
- a trusted CAN timestamp;
- a scalable analysis method;
- an event schema;
- a quantitative acceptance criterion;
- an end-to-end software architecture.

The available viewer supported inspection but not an efficient, exportable
analysis workflow. Some early exported Camera values were unusable. The source
CAN therefore had to be decoded directly from raw bytes with DBC definitions.

The engineering task consequently expanded from "inspect a video" into four
connected problems:

1. create trustworthy, time-ordered and traceable analysis data;
2. define Camera-Radar discrepancy without pretending Radar is ground truth;
3. compress large datasets into a small set of useful candidate windows;
4. connect every candidate back to video and CAN evidence for human review.

Early independent GUI programs solved parts of the problem but accumulated
overlapping sorting, missing-value and analysis responsibilities. The current
U001/U002/U003 architecture replaces that tool-by-tool growth with explicit
program boundaries, shared contracts and governed acceptance.

2. MISSION, VALUE AND SUCCESS DEFINITION
======================================================================

2.1 Mission

Build a traceable and extensible engineering analysis foundation that reduces
large Camera, Radar and vehicle-CAN datasets to a small number of high-value,
video-reviewable investigation candidates.

2.2 Short-term value

- reduce the amount of video an engineer must inspect manually;
- produce start, peak and end FrameCount for candidate events;
- expose the signals and conditions associated with each candidate;
- distinguish data-quality, association and sensor-discrepancy questions;
- create evidence suitable for engineering discussion and reporting;
- preserve enough provenance to reproduce every result.

2.3 Medium-term value

- automate broad screening of hundreds of heterogeneous CAN variables;
- stabilize baseline, residual, threshold and event-merging methods;
- compare conditions and scenarios across the complete recording;
- validate repeatability across additional logs;
- introduce controlled dynamic analysis when the sample domain permits it.

2.4 Long-term value

The project may become one component of a larger data-analysis foundation and
support future adapters for MATLAB/Simulink, System Identification, ROS,
Autobox, LiDAR, remote workstations or cloud/data-center processing.

These are compatibility directions, not current implementation commitments.

2.5 Definition of project success

The first complete success condition is one Golden Run that can demonstrate:

  immutable source identity
  -> accepted U001 data package
  -> declared U002 analysis configuration
  -> candidate Event Queue and narrow Review Data
  -> U003 synchronized review
  -> review disposition and evidence export
  -> reproducible report

Success is not measured by the number of algorithms or GUI features added.
Success is measured by useful candidate compression, traceability,
reproducibility, review efficiency and honest treatment of uncertainty.

4. CONFIRMED FACTS, OBSERVATIONS AND OPEN HYPOTHESES
======================================================================

4.1 Confirmed facts

- Radar is a provisional engineering reference, not ground truth.
- Camera-Radar difference must be called discrepancy unless independent
  ground truth is available.
- The current CAN timestamps are not trusted for video alignment.
- FrameCount is the authoritative video-domain key for the current profile.
- FrameCount is approximately 20 Hz and is not a high-resolution timestamp.
- One FrameCount can contain multiple message and signal updates.
- The source contains heterogeneous numerical, Boolean, enum, bitfield,
  counter, identifier and state signals.
- Missing, no-update, stale, invalid-default, false/zero and unavailable are
  different data states.
- Unlimited forward fill and global blank-to-zero filling can create false
  continuity and false dynamics.
- Recognition_ID maps to Camera message references, but video validation
  rejected it as a reliable standalone active-target selector.
- Camera-side continuity can produce useful provisional trajectories, but
  continuity alone cannot prove target identity.
- Existing data has shown Camera no-target/default behavior such as 327.66.
  Other sentinel values require signal-specific confirmation.
- U001 and U003 have passed their current release acceptance.
- U002 has not yet been implemented as the governed middle product.

4.2 Important engineering observations

- A descriptive Camera-Radar discrepancy near two metres was observed in one
  provisional selector dataset.
- Earlier exploratory distance bins suggested the discrepancy may increase
  with distance over the observed range.
- This trend is not yet approved as a formal baseline because Camera target
  identity is unresolved in part of the data.
- Video review exposed intervals where the visible target remained stable but
  CAN-selected Camera source information appeared inconsistent.
- Camera target loss, Radar target mismatch, definition-point differences,
  road curvature and synchronization effects can all create apparent
  discrepancy.

4.3 Active hypotheses

- normal discrepancy contains distance-dependent structure;
- lateral position, vehicle attitude, road curvature and motion state may
  modify residual behavior;
- some large discrepancies arise from target association rather than sensor
  measurement error;
- some residuals may show persistence, delay or dynamic input dependence;
- high-risk behavior may be concentrated in specific condition combinations
  or continuous event windows;
- display target, control target and CAN-reported reference may not always be
  the same system identity.

Hypotheses are not conclusions. Each requires an Experiment and a Decision.

5. TERMINOLOGY AND CLAIM DISCIPLINE
======================================================================

ReferenceValue
  The signal declared as the provisional comparison reference for one
  analysis. It is not automatically truth.

TargetValue
  The signal compared with the declared reference.

RawDiscrepancy
  The signed difference between the declared reference and target:

    d(t) = ReferenceValue(t) - TargetValue(t)

  The opposite sign may be configured, but the sign convention must be stored
  in the Run Manifest.

Baseline
  An estimate of normal or expected discrepancy under declared conditions.

Residual
  The discrepancy remaining after the approved baseline is removed:

    r(t) = d(t) - b(x(t))

PredictionError
  The difference between an observed dynamic outcome and a model prediction.
  It is not interchangeable with static residual.

AnomalyScore
  A declared numerical ranking score calculated from valid residual evidence.
  The score definition must be versioned.

CandidateFrame
  A frame that meets the configured screening rule. It is not yet a confirmed
  event.

EventHint / CandidateWindow
  A continuous or merged interval sent to engineering review.

ReviewedEvent
  A candidate window with an explicit human disposition and evidence.

RootCause
  A causal engineering conclusion supported by independent system evidence.
  Association, correlation or a large residual alone does not establish it.

CameraError / RadarError
  These terms require reliable truth or an independently justified reference.
  They must not be used for raw Camera-Radar difference by default.

8. U001 DATA CONTRACT SUMMARY
======================================================================

8.1 Two order domains

Source update order:

- SourceRowIndex preserves exported CAN row order;
- it provides within-frame ordering evidence;
- it is not automatically physical time.

FrameCount domain:

- the authoritative current video-synchronization domain;
- approximately 20 Hz;
- used for static discrepancy, event localization and U003 review;
- must not be silently replaced by untrusted CAN time.

Frame assignment propagates metadata labels to source rows. It is not
measurement forward fill.

8.2 Mixed signal semantics

ValueKind:

- FLOAT
- INTEGER
- BOOLEAN
- ENUM
- BITFIELD

SignalRole:

- MEASUREMENT
- STATE
- EVENT_FLAG
- VALIDITY_FLAG
- COUNTER
- IDENTIFIER
- FRAME_KEY

UpdateMode:

- PERIODIC
- ON_CHANGE
- EVENT
- UNKNOWN

Boolean zero is normally a valid state. Event flags must not be held across
frames. Unknown semantics remain explicit and provisional.

8.3 Missingness and hold

Prohibited defaults:

- global blank-to-zero conversion;
- unlimited measurement forward fill;
- hidden interpolation.

Allowed hold:

  NONE
  HOLD_LAST_BOUNDED

Every held value must expose age and validity. A numerical value alone does
not prove freshness.

8.4 U001 controlled six-file package

D1 u001_decoded_updates.csv
  Long-form real decoded updates with source and FrameCount provenance.

D2 u001_frame_values.csv
  One row per canonical FrameCount. Each signal group includes:
  value, label, updated, update_count, age, valid and missing_reason.

D3 u001_signal_catalog.csv
  Signal definitions, units, types, roles, validity, aggregation and hold
  policies.

D4 u001_quality_report.csv
  Global and per-signal data-quality metrics.

D5 u001_run_manifest.json
  Dataset/run identity, versions, configurations, hashes and file inventory.

D6 u001_review_view.csv
  Narrow human-readable view. It is not a substitute for D1-D5.

8.5 U001 processing modes

CONTROLLED_PROFILE:

- versioned, approved signal selection and policy;
- used for reproducible formal analysis.

AUTO_DISCOVERY:

- selects every technically eligible decodable signal;
- splits signals into deterministic bounded-width shards;
- uses conservative provisional policy;
- lets U002 rank relevance;
- does not claim statistical or causal importance.

Approved closed loop:

  AUTO_DISCOVERY
  -> U002 screening
  -> proposed signal-promotion request
  -> engineering approval
  -> new CONTROLLED_PROFILE
  -> U001 rerun
  -> formal U002 conclusion

9. U002 FORMAL DEVELOPMENT TARGET
======================================================================

9.1 U002 first product objective

Consume one immutable accepted U001 package and produce the smallest traceable
Camera-Radar investigation output:

1. validate contract, manifest, hashes and quality evidence;
2. declare analysis domain, reference, target, unit and sign;
3. apply an explicit analysis-eligibility mask;
4. calculate provisional RawDiscrepancy;
5. fit one approved distance-dependent baseline on eligible data;
6. calculate residual;
7. calculate one approved robust candidate score;
8. apply threshold and persistence;
9. merge frames into candidate windows;
10. rank candidates;
11. export U003 Event Queue and narrow Review Data;
12. preserve full configuration and evidence.

9.2 Fail-closed input rules

U002 must stop when:

- U001 completion code or ReadyForU002 is false;
- contract/schema version is unsupported;
- dataset, run, request or source identity conflicts;
- required files or hashes fail;
- FrameCount is missing, nonnumeric, duplicated or out of order;
- required units or signals cannot be resolved;
- blocking quality findings exist;
- the selected analysis region contains no eligible rows.

U002 must not "best effort" its way through a broken contract.

9.3 Analysis domains

FRAME_DOMAIN:

- one sample per canonical FrameCount;
- valid for static discrepancy, baseline, residual and video-linked events;
- approximately 20 Hz in the current profile.

UPDATE_DOMAIN:

- real source update sequence;
- used for update evidence and future carefully designed dynamic work;
- does not provide trustworthy seconds without a validated timestamp.

Delay, memory and gain claims must state the actual sample domain and its
limitations.

9.4 U002 output families

Machine analysis outputs:

- analysis configuration and Run Manifest;
- row-level eligibility and exclusion reason;
- RawDiscrepancy, baseline, residual and anomaly score;
- global and conditional metrics;
- variable-ranking evidence;
- event-level metrics;
- warnings and model applicability.

Promotion output:

- proposed signal shortlist for controlled U001 rerun;
- reason, evidence and semantic warnings for each signal.

U003 outputs:

- Event Queue with Event ID, start, peak and end FrameCount;
- narrow Review Data with only human-useful comparison fields;
- review instructions and expected disposition codes.

Reporting outputs:

- plot-ready CSV by default;
- XLSX or presentation only when human reporting requires it;
- method, assumptions, limitations and review status.

10. ANALYSIS AND MATHEMATICAL METHOD MAP
======================================================================

Methods are classified as FORMAL BASELINE, PROVISIONAL, LEGACY/REVIEW,
PLANNED EXPERIMENT or DEFERRED. Being implemented in an older program does not
automatically make a method formally approved.

10.1 Data-quality gate - FORMAL REQUIREMENT

Before numerical analysis:

- verify FrameCount and source identity;
- verify valid/updated/age/missing_reason fields;
- verify units and signal roles;
- reject invalid sentinels;
- record target-association confidence;
- separate unusable rows from usable rows.

No statistic can repair an invalid comparison population.

10.2 Raw discrepancy - FORMAL CONCEPT

  d(t) = R(t) - T(t)

where R is the declared provisional reference and T is the declared target.
The configuration records sign, units, valid population and association rule.

10.3 Conditional baseline - PROVISIONAL METHOD TO VALIDATE

A robust first candidate is a conditional median baseline:

  b1(x_bin) = median(d | x in x_bin, eligible)
  r1(t)     = d(t) - b1(x(t))

Possible x:

- reference distance;
- Camera distance;
- another physically justified conditioning axis.

Why median:

- more robust than mean to isolated large discrepancies;
- simple to explain and audit.

Assumptions:

- most eligible samples in a bin represent normal behavior;
- target association and validity are adequate;
- each bin has sufficient support;
- bin width does not hide important structure.

Required evidence:

- sample count per bin;
- median and robust spread;
- missing/invalid fraction;
- candidate fraction;
- stability across data segments;
- residual dependence after correction;
- video review of candidate enrichment and false positives.

10.4 Multi-stage baseline - LEGACY / REQUIRES REVALIDATION

Legacy P004 supports:

  Stage1BaselineGap = median(RawDiscrepancy | Stage1AxisBin)
  ResidualStage1    = RawDiscrepancy - Stage1BaselineGap

and optional:

  Stage2BaselineGap =
      median(ResidualStage1 | Stage1Bin, Stage2AxisBin)
  ResidualStage2 = ResidualStage1 - Stage2BaselineGap

Formal adoption requires proof that Stage 2:

- has a physical purpose;
- improves out-of-sample structure;
- does not absorb true anomalies;
- has sufficient data support;
- justifies added complexity.

More stages are not automatically better.

10.5 Robust anomaly score - PLANNED EXPERIMENT

The first score should be simple, declared and reproducible. Candidate forms
include robust scaling of residual by median absolute deviation or another
approved robust scale.

No score is formal until an Algorithm Card defines:

- equation;
- zero-scale handling;
- training/reference population;
- threshold;
- missingness rules;
- expected direction;
- validation experiment.

10.6 Threshold, persistence and event merging - PLANNED FORMAL CORE

Frame thresholding alone produces noisy candidates. U002 must define:

- threshold rule;
- minimum persistent frames or duration;
- permitted interruption gap;
- event merge gap;
- start, peak and end definitions;
- event severity;
- reason codes;
- complete-window eligibility.

An Event Hint remains a candidate until reviewed.

10.7 Variable screening - PLANNED

Candidate techniques:

- Pearson correlation for linear association;
- Spearman correlation for monotonic association;
- normalized mutual information for broad nonlinear dependence;
- robust conditional differences;
- candidate enrichment by signal bins;
- cross-correlation or lag scan under an explicit sample domain.

Screening output means "investigation priority", not causal influence.

Safeguards:

- exclude counters, identifiers and technical metadata from inappropriate
  numerical ranking;
- respect ValueKind and SignalRole;
- control sparse categories and minimum support;
- treat held values and age explicitly;
- correct for repeated testing or use stable cross-segment ranking;
- promote shortlisted variables into a controlled profile before conclusions.

10.8 Conditional and scenario analysis - PLANNED

One-dimensional and two-dimensional bins may identify local high-risk
conditions using:

- count;
- residual robust spread or upper quantile;
- conditional candidate rate;
- enrichment relative to global candidate rate;
- missingness and association-confidence controls.

Global candidate rate and conditional candidate rate are different metrics and
must not share an ambiguous label.

10.9 Dynamic analysis and System Identification - DEFERRED

Possible later questions:

- Does residual have memory?
- Which past variables improve prediction?
- What delay is supported?
- Does the dynamic relation change by scenario?
- Is the final prediction error closer to white noise?

Candidate models:

  r(t) = sum_i a_i r(t-i)
       + sum_j b_j u_j(t-d_j)
       + e(t)

Potential methods:

- ACF/PACF;
- AR;
- ARX;
- prediction-error models;
- residual whiteness tests;
- cross-validation by time segment;
- state-space models when justified.

Dynamic work is not authorized until:

- target association is controlled;
- sample domain and interval are valid;
- artificial memory from hold/aggregation is excluded;
- static baseline and event workflow are stable;
- training and validation segments are separated.

10.10 Root cause - ENGINEERING REVIEW OUTPUT, NOT A STATISTIC

Root cause may require:

- video;
- target tracking and object identity;
- Radar detection state;
- system/HMI state;
- signal validity;
- road geometry and vehicle motion;
- source definitions and reference points;
- system specifications;
- reproducibility across logs.

U002 provides evidence and hypotheses. It does not replace engineering
judgment.

11. TARGET ASSOCIATION STRATEGY
======================================================================

Target association is a formal quality gate, not a cosmetic preprocessing
choice.

Current status:

- multiple Camera object messages can carry plausible values;
- Recognition_ID is not accepted as the active displayed/control-target
  selector;
- a Camera1/Camera3 continuity method is retained as a provisional
  preprocessing hypothesis;
- continuity confidence is model confidence, not target-identity truth;
- Radar must not be used to choose the Camera value closest to Radar, because
  that would minimize discrepancy by construction.

Allowed current paths:

- analyze visually unambiguous intervals;
- use a provisional Camera-side selector with explicit CONFIDENT, AMBIGUOUS
  and INVALID states;
- exclude ambiguous intervals from baseline fitting;
- continue investigating the authoritative display/control target signal;
- validate any new selector on deterministic video episodes before adoption.

The exact relationship among displayed target, controlled target, track ID and
reference signal remains an Open Question.

Responsibilities:

- define delivery priorities and intended engineering use;
- provide authoritative signal/system knowledge;
- review candidate findings and reports;
- decide when system-specific conclusions may be communicated externally.

13.4 Conflict resolution

When implementation output conflicts with the approved specification:

1. preserve the last passing boundary;
2. record the first failing boundary;
3. identify whether the defect is in product, test, validator, contract or
   execution;
4. obtain independent evidence;
5. repair only the owning layer;
6. rerun the complete applicable acceptance chain.

A validator must not be weakened merely to make unexplained differences pass.

14.3 Software evidence layers

These are different and must not be conflated:

- source self-test;
- independent conformance Gate;
- integration test;
- performance/capacity test;
- packaged-runtime test;

14.4 Performance progression

Required sequence:

  self-test
  -> small fixture
  -> 10k scale
  -> 40k scale
  -> full source

Record:

- input and output rows;
- elapsed time;
- peak memory;
- worker behavior;
- blocking errors;
- semantic-equivalence evidence.

Stop on unexplained sustained memory growth. Optimization must preserve output
semantics against a frozen reference.

14.5 Release freeze

A frozen product reopens only for:

- a reproducible defect;
- a downstream interface blocker;
- an approved semantic-preserving performance change;
- an explicit new business requirement with a Decision entry.

Cosmetic curiosity is not sufficient reason to reopen a release.

15. TECHNICAL AND OPERATIONAL CONSTRAINTS
======================================================================

15.1 Data-transfer constraint

Company data, video, DBC, internal source, execution logs and internal
documents remain inside the approved company environment and are not uploaded
to personal or public systems.

When generic implementation assistance is required, only permitted,
non-file-based technical descriptions are used, such as:

- schema and headers;
- compact counts and metrics;
- error messages;
- equations and parameter summaries;
- short behavior memos;
- return capsules;
- approved business context.

Generic designs, study materials and non-company-specific tools may enter the
company environment through an approved one-way download path.

15.2 Low-bandwidth human return channel

The human operator is the bottleneck. Therefore:

- long specifications are delivered as files;
- normal success returns use one compact capsule;
- failures identify layer, artifact, cause and next evidence;
- free text is limited to one to three short memos;
- long hashes and large tables are not manually transcribed;
- output files state where the next return capsule is located.

15.3 Current environment

- company execution is Windows-based;
- U001 portable release targets compatible company Windows hosts, not all
  operating systems;
- U003 is accepted as a one-file Windows EXE;
- Python source deliveries use an additional final .txt during transfer;
- company endpoint protection and file locks can affect packaged applications;
- CMD instructions are preferred for company execution where applicable.

15.4 Scale

- hundreds of signals may be available;
- a full source may contain millions of decoded updates;
- wide human tables are unusable;
- one monolithic 700-signal provenance-rich table is prohibited;
- machine outputs may be broad/sharded;
- human review outputs remain intentionally narrow.

15.5 Evidence limitations

- no reliable general ground truth is currently available;
- one principal log/video cannot prove generalization;
- video display may not equal control target;
- within-frame order is not physical time;
- U003 mapping depends on a confirmed anchor;
- explicit lag is a review aid, not automatically true latency.

16. RISK REGISTER
======================================================================

R01 Target-association error
  Effect: artificial Camera-Radar discrepancy and false anomaly.
  Control: explicit association status, video validation, exclusion from
  baseline, authoritative-signal investigation.

R02 Time-domain misuse
  Effect: incorrect delay, event or SysID claims.
  Control: FrameCount-domain declaration, source-order provenance, no invented
  sub-frame time.

R03 Missingness destruction
  Effect: fake zeros, fake continuity and fake dynamics.
  Control: Data Contract validity/missing_reason/updated/age fields.

R04 Overfitted baseline
  Effect: true anomalies absorbed as normal.
  Control: physical justification, minimum support, held-out segments and
  video-reviewed candidates.

R05 Multiple-variable false discovery
  Effect: unstable high-ranked signals among hundreds of variables.
  Control: semantic filtering, stable cross-segment ranking, promotion and
  controlled rerun.

R06 Circular target selection
  Effect: Camera source selected because it matches Radar, artificially
  reducing discrepancy.
  Control: keep Radar out of Camera target-selection cost.

R07 Program responsibility drift
  Effect: overlapping cleaning, analysis and event logic.
  Control: U001/U002/U003 matrix and formal interface changes.

R08 Implementation-tool context loss
  Effect: code diverges from design.
  Control: complete step-by-step packet, exact filenames, fresh implementation
  session, independent Gate.

R09 Resource exhaustion
  Effect: multi-hour runs or host instability.
  Control: streaming, bounded state, staged capacity tests and profiling.

R10 Packaging/environment failure
  Effect: program works only in development environment.
  Control: packaged import tests, no-argument GUI test and target-host runtime
  acceptance.

R11 Reporting overclaim
  Effect: discrepancy represented as proven Camera error or root cause.
  Control: terminology discipline and explicit evidence level.

R12 Scope expansion
  Effect: new event types, SysID and platform features delay Golden Run.
  Control: current milestone priority and Complexity Control.

Date: 2026-07-28
Status: IMPLEMENTATION SPECIFICATION - SINGLE PROCESS REFERENCE

======================================================================
1. PURPOSE
======================================================================

Replace repeated per-row DBC decoding with a change-driven message cache while
preserving one deterministic frame-level current-state output for every
configured signal.

This v0.4A is deliberately single-process.  It becomes the semantic reference
for the later multiprocessing v0.4B.  Do not add ThreadPoolExecutor,
ProcessPoolExecutor or multiprocessing in v0.4A.

4. SOURCE REPRESENTATION AND TERMINOLOGY
======================================================================

Declare:

SourceRepresentation = BUFFER_SNAPSHOT_WIDE
RawByteEncoding = HEX_TEXT
RawByteDigitsOnlyBase = 16
ObservationSemantics = SNAPSHOT_STATE_CHANGE

Required meanings:

- SNAPSHOT_OBSERVED: a complete valid payload is visible in one source row;
- PAYLOAD_STATE_CHANGE: current normalized payload differs from the previous
  valid normalized payload for the same Channel/CAN-ID/DLC group;
- PAYLOAD_REUSED: current valid payload equals the cached payload;
- BUS_UPDATE: unknown and must not be claimed by this source adapter.

Do not label nonblank repeated payloads as physical CAN updates.
Do not claim measured bus cadence from source-row repetition.

If existing output column names contain `update_count`, retain the columns for
schema compatibility but declare in quality/manifest metadata:

UpdateCountSemantics = SIGNAL_STATE_CHANGE_OBSERVED

Do not silently describe these counts as CAN transmission counts.

======================================================================
5. AUTHORITATIVE FRAME KEY
======================================================================

Keep exactly:

- Channel 2;
- CAN ID 0x620;
- exact DBC SignalName FrameCount;
- FRAME_KEY role.

0x620 contains five signals.  The other four never become Frame keys by
sharing the Message ID.

FrameCount processing remains serial and deterministic.

For the Frame-key message:

1. normalize the hexadecimal payload;
2. on first valid payload, decode exact FrameCount;
3. on a changed valid payload, decode exact FrameCount;
4. on an identical repeated payload, reuse cached FrameCount without DBC
   decode;
5. equal FrameCount observations remain allowed;
6. a decrease/reset/wrap remains blocking under the accepted current policy;
7. EOF finalizes the last open frame exactly once.

======================================================================
6. MESSAGE-LEVEL CHANGE CACHE
======================================================================

Create one runtime cache per required message group keyed by the accepted exact
identity:

(Channel, normalized CAN ID, DLC)

Each cache must contain at least:

- last_valid_normalized_payload;
- current decoded values for every configured signal in that message;
- last_snapshot_observed_source_row;
- last_payload_change_source_row;
- per-frame signal-state-change counters;
- current validity state;
- bounded diagnostic counts only, no Raw payloads in quality JSON.

For each source row and required message group:

A. all cells missing:

- mark SNAPSHOT_MISSING for that source row;
- do not decode;
- do not replace cached value with zero;
- do not claim a payload change.

B. partial or invalid payload:

- mark SNAPSHOT_INVALID;
- do not decode;
- preserve the last valid cache internally for diagnostics only;
- frame output validity must follow accepted validity/hold policy, not silently
  present the invalid row as current valid data.

C. first complete valid payload:

- normalize using the accepted canonical hex parser;
- decode the configured signals once;
- initialize the cache;
- classify INITIAL_STATE_OBSERVED;
- count one payload decode.

D. complete valid payload different from cache:

- decode configured signals once;
- compare each decoded signal with its cached decoded value using exact RawCode
  and deterministic physical-value equality rules already accepted;
- increment a signal state-change count only when that signal changes;
- update cache;
- classify PAYLOAD_STATE_CHANGE;
- count one payload decode.

E. complete valid payload identical to cache:

- do not call any DBC signal decoder;
- do not create 705 repeated per-signal update objects;
- update last_snapshot_observed_source_row and snapshot-presence state;
- reuse cached decoded values;
- classify PAYLOAD_REUSED.

The last valid payload cache must persist across pandas chunks.

======================================================================
7. FRAME-LEVEL STATE OUTPUT
======================================================================

The accepted output remains one row per finalized FrameCount per batch shard.

At frame finalization, for each configured signal:

- output the current decoded cached value if its parent snapshot was valid and
  observed under the accepted policy;
- output the accepted invalid/missing status otherwise;
- preserve RawCode and PhysicalValue separately;
- preserve ValueKind, role, unit and validity metadata;
- never fill missing with zero;
- never apply unlimited forward fill;
- never convert an unchanged snapshot into a new signal state change;
- do not omit a frame merely because its payload repeated.

The current state must therefore remain available on repeated frames even when
the expensive DBC decode was skipped.

For EVENT_FLAG signals:

- preserve current state at each frame;
- record every decoded state change within the frame;
- EVENT_FLAG remains never held across a missing/invalid parent snapshot;
- do not invent an event from a repeated zero/default value;
- do not discard a transient decoded active state that occurred within the
  frame if the accepted configuration defines ANY_ACTIVE_WITHIN_FRAME;
- if active aggregation is not configured, preserve the existing deterministic
  last-state rule and record a warning rather than inventing semantics.

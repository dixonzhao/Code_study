U001 DATA PREPARATION WORKBENCH GUI v0.1 — SPECIFICATION
Date: 2026-07-27

======================================================================
1. ARCHITECTURAL ROLE
======================================================================

The GUI is a thin control-plane client of:

u001_g8a_thin_orchestrator_v0_4.py

The accepted backend remains the sole owner of:

- Gate discovery and hashes;
- config fingerprinting;
- Preflight;
- Gate 1–Gate 7 execution order;
- protected-input checks;
- six-file package completion;
- backend capsules and orchestration manifest.

The GUI does not import Gate modules or reimplement their transformations.

======================================================================
2. GUI v0.1 FUNCTIONS
======================================================================

- auto-detect UDP001 and one prepared Case;
- display/edit UDP001, Case, orchestrator, config, Preflight, and Run paths;
- display/edit DatasetId, RunId, SegmentId, SourceId, and MaxSourceRows;
- launch G8A2 self-test;
- create a non-overwriting G8A2 config;
- launch Preflight and parse its capsule;
- lock Run until current-session Preflight passes;
- launch all nine backend stages;
- monitor stage count from the backend orchestration manifest;
- display stdout/stderr and backend capsules;
- open the Run output folder;
- cancel only the process tree started by this GUI;
- write one GUI acceptance capsule.

======================================================================
3. SAFETY BOUNDARY
======================================================================

The GUI must not:

- decode CAN;
- edit source CSV/DBC files;
- edit Gate programs or control CSVs;
- sort, fill, classify, aggregate, hold, or fuse data;
- overwrite config, Preflight output, or Run output;
- hide a failed backend return code;
- claim physical-signal correctness;
- calculate discrepancy, baseline, residual, or Event;
- run U002 Analyzer logic.

Every subprocess uses sys.executable, an argument list, and shell=False.

======================================================================
4. ACCEPTANCE CAPSULE
======================================================================

U001GUI1
N-Tt-Cc-Pp-Rr-Ss-Ll-Xx
C-n

T = G8A2 self-test passed in this GUI session
C = config successfully created by this GUI session
P = Preflight passed in this GUI session
R = backend Run passed in this GUI session
S = backend completed stages, expected 9
L = backend orchestration manifest exists, expected 1
X = failed GUI acceptance conditions, expected 0

PASS:

T1 C1 P1 R1 S9 L1 X0 C-0

The backend G8A2 capsule must also independently return C-0.

======================================================================
5. WHY THIS RUN IS STILL NOT FINAL PRODUCT ACCEPTANCE
======================================================================

GUI Run B proves that the accepted backend can be operated through one GUI.
It does not by itself prove Run A/Run B output reproducibility.

After both capsules pass, a new minimal read-only comparator will check:

- D1 exact equality;
- D2 exact equality;
- D3 semantic keyed equality;
- D4 semantic keyed equality;
- D6 exact equality;
- D5 internal integrity and only explicitly permitted runtime differences.

This comparison replaces the archived G8B/G8R validator line. It will not
restore blind whole-manifest equality or compare a file against itself through
duplicated reference/candidate structural checks.

======================================================================
6. PRODUCTIZATION AFTER REPLAY ACCEPTANCE
======================================================================

After GUI replay acceptance:

1. move the accepted GUI to 01_PROGRAMS;
2. add New Case signal inventory/selection workflow without changing the Data
   Contract;
3. execute one full-source controlled run;
4. package the stable GUI and Python runtime for Windows using PyInstaller;
5. retain CLI operation as a diagnostic/automation fallback.

Only then may U001 v0.1 be marked PRODUCT ACCEPTED.

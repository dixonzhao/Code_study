UDP002 U22B1B0 - 真实 Signal Semantic Binding Gate
版本：v0.1
日期：2026-08-20

一、这一步解决什么问题

真实 U001→U002 S0 衔接已经通过，但 B1B 不能直接在代码中猜测列名，也不能
因为当前测试车使用特定 CAN ID 就把算法写死。

U22B1B0 从刚刚通过的真实 U001_INTAKE_ACCEPTED Artifact 中读取 metadata-only
Signal Inventory，并生成一个 provisional binding proposal。

它只回答：

- 哪个 governed signal 是 Camera 1 Distance；
- 哪个是 Camera 3 Distance；
- 哪个是 Radar Distance；
- 哪个是 Radar Detection Flag；
- 哪个是 Vehicle Speed；
- 哪个是原始 FrameCount source signal。

它不读取或复制业务信号值，不执行 continuity arbitration，不生成异常候选。

程序会自动选择最新的 `REAL_U001_HANDOFF_ACCEPTED` B1AR Run，并读取其中唯一的
u001_signal_inventory.csv。

五、返回码含义

成功格式：

U22B1B0 N-K?-F?-C1?-C3?-RD?-RF?-VS?-FC?-U?-D?-B0-P1-I1-X0 C-0

K  = D3 catalog signal 总数
F  = IncludeInFrameView=1 的 signal 数量
C1 = Camera 1 Distance 匹配数
C3 = Camera 3 Distance 匹配数
RD = Radar Distance 匹配数
RF = Radar Detection Flag 匹配数
VS = Vehicle Speed 匹配数
FC = FrameCount source 匹配数
U  = 尚未归入上述六个角色的 signal 数量
D  = 出现多重匹配的角色数量
B  = blocking required-role 数量
P1 = provisional binding proposal 已生成
I1 = source inventory 运行前后未改变

Camera 1 和 Camera 3 是 B1B 的 required roles，必须各且仅有一个匹配。
Radar、Flag、Speed 和 FrameCount 在当前 B1B0 中记录为 optional metadata；缺失时不会
为了凑数自动猜测。

六、生成文件

程序会在 04_TEMP 生成：

u22b1b0_signal_binding_proposal_<inventory-hash>.json

该文件保存 exact CanonicalName、CAN ID、Channel、SignalName、Unit、ValueKind、
HoldPolicy、MaxAgeFrames 及源 Artifact hash。后续 B1B Module 使用这份 proposal
生成显式 Run Configuration，不需要再次猜列名。

当前不要手工编辑或移动该 JSON；等 B1B binding acceptance 后再受控提升到
02_CONFIG/binding_profiles。

七、回传

只回传正式运行的一行，不回传 self-test：

如果 C-7，停止；不要修改 inventory 或匹配规则。

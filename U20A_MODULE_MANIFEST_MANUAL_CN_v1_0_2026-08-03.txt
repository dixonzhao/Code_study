U002 MODULE MANIFEST中文说明书

版本：1.0
日期：2026-08-03
Owner：Zhao Zhili
适用对象：第一次接触模块化分析系统的开发者、维护者和分析工程师


一、读完后应该会什么

读完后，你应该能够：

1. 用一句话解释Module Manifest是什么；
2. 判断一个Module属于U002的哪个Stage；
3. 区分源信号输入与上游Artifact依赖；
4. 判断一个Module失败后应该阻断什么；
5. 解释为什么多个Module不能任意覆盖同一输出；
6. 从Manifest确认具体实现、配置和版本身份；
7. 在不打开Module代码的情况下判断它能否被Registry加载。


二、一句话定义

Module Manifest是一份机器可读的“模块岗位说明书、接口契约和身份证”。

它不包含算法正文，但它必须准确说明：

- Module是谁；
- 它属于哪个Stage；
- 它解决什么类型的问题；
- 它需要哪些输入；
- 它依赖哪些上游结果；
- 它会提供哪些输出；
- 它失败时怎样处理；
- 它与哪些Engine版本兼容；
- 当前代码内容究竟是哪一份。


三、它在U002架构中的位置

U002固定Stage：

  S0 Intake and Contract Gate
  S1 Semantic Reconstruction and Analysis Preprocessing
  S2 Analysis View and Population Construction
  S3 Primary Outcome Construction
  S4 Baseline and Residual
  S5 Evidence Engines
  S6 Candidate Synthesis
  S7 Handoff and Export

每个Stage内部可以安装一个或多个Module Pack。

Module Manifest位于Module Pack最外层。Registry刷新模块目录时，先读取Manifest，而不是直接import Python代码。

  modules/
    S1/
      camera_target_selector/
        module_manifest.json
        configuration_schema.json
        camera_target_selector.py
        algorithm_card.txt
        tests/

Registry工作顺序：

1. 找到module_manifest.json；
2. 检查Contract和字段；
3. 检查ModuleId、版本、Stage和Engine兼容性；
4. 检查依赖与输出冲突；
5. 检查ImplementationSha256；
6. 运行声明的SelfTest；
7. 通过后才将Module加入可选列表。

这样做的关键价值是：

> 一个损坏、未知或不兼容的Module不能在Workbench启动时通过import直接拖垮整个程序。


四、现实工程意义

没有Module Manifest时，常见开发方式是：

  在主程序里import一个新文件
  -> 给它传几个DataFrame
  -> 它增加或修改一些列
  -> 运行成功就认为功能完成

这种方式短期很快，长期会出现：

- 不知道模块需要哪些列；
- 不知道它悄悄改了哪些列；
- 不知道它属于预处理、分析还是Candidate；
- 相同列名被不同函数反复覆盖；
- 参数改变后报告无法追溯；
- 模块升级后旧实验无法重现；
- 可选功能失败却让整个程序崩溃；
- 实验方法未经批准就进入正式Pipeline。

Module Manifest把这些隐含关系变成显式、可检查的契约。

在现实团队协作里，它允许新成员先读Manifest就回答：

- 这个Module是否适合我的Case？
- 我需要准备什么输入？
- 它的输出能否接到下一个Module？
- 它目前是正式算法还是实验算法？
- 如果它失败，我还能不能得到其他结果？


五、实际阅读文件

打开：

  .\U-UDP002\05_TESTS\01_FIXTURES\U20A_v0_1\valid_module_manifest.json

不要从上到下机械背字段。按照以下七步阅读。


STEP M1：确认身份

字段：

  ContractType
  ContractVersion
  ModuleId
  ModuleVersion
  DisplayName
  Description


1. ContractType

本例：

  U002_MODULE_MANIFEST

意义：

告诉Validator这份JSON应该按照Module规则检查，而不是按照Artifact或Run规则检查。


2. ContractVersion

本例：

  0.1

意义：

表示这份Module Manifest采用U002 Core Contract 0.1格式。

它不是算法版本。


3. ModuleId

本例：

  U002.S1.CameraTargetSelector

意义：

这是Module的稳定逻辑身份。文件名、显示语言或目录位置可以变化，但ModuleId不能随意变化。

推荐结构：

  U002.<Stage>.<FunctionalName>


4. ModuleVersion

本例：

  0.1.0

意义：

表示CameraTargetSelector自身的实现版本。

必须区分：

  ContractVersion = Manifest公共格式版本
  ModuleVersion   = 具体算法模块版本

以后Contract仍然是0.1时，Module可能已经升级到0.3.0。


5. DisplayName与Description

DisplayName给GUI和人阅读。

Description用一句或几句话说明模块目的，但不能代替Algorithm Card。

Manifest回答“接口和身份”；Algorithm Card回答“数学方法为什么成立”。


STEP M2：确认职责边界

字段：

  Stage
  ModuleKind
  AlgorithmStatus
  ExecutionRequirement


1. Stage

本例：

  S1

意义：

Camera Target Selection属于语义重建，不属于Baseline或Evidence。

Stage是架构中的位置，不是程序文件执行到第几行。


2. ModuleKind

本例：

  SEMANTIC_BUILDER

意义：

它把多个源观测构造成一个有工程含义的语义对象，例如Canonical Camera Target。

当前允许的Kind与Stage对应：

  S0  INTAKE_GATE
  S1  VALIDITY_PREPROCESSOR / SEMANTIC_BUILDER / ARBITRATION / ANALYSIS_VIEW
  S2  ANALYSIS_VIEW
  S3  PRIMARY_OUTCOME
  S4  BASELINE
  S5  EVIDENCE
  S6  CANDIDATE_SYNTHESIS
  S7  HANDOFF_EXPORT

错误示例：

  Stage = S1
  ModuleKind = BASELINE

这会被Validator拒绝，因为Baseline不能伪装成语义预处理。


3. AlgorithmStatus

本例：

  PROVISIONAL

四种状态：

  FORMAL
    已通过Experiment与Decision，进入正式Pipeline。

  PROVISIONAL
    当前可以推进工程，但必须保留限制和不确定性。

  EXPERIMENTAL
    只用于实验比较，不能自动影响正式结果。

  DEPRECATED
    已废弃，只能用于历史恢复，不能进入新Run。

现实意义：

Camera 1/3连续性选择目前经过了一定视频验证，但尚不能等同于车辆系统真正使用目标，因此应该是PROVISIONAL，而不是FORMAL。


4. ExecutionRequirement

本例：

  REQUIRED

意义：

这条Run路径依赖该Module。它失败后，依赖它的分析不能继续宣称成功。

注意：

AlgorithmStatus与ExecutionRequirement是两个维度。

一个PROVISIONAL算法仍可能是当前Golden Run的REQUIRED Module；这表示当前路径必须使用它，但结论仍需标记暂定。


STEP M3：确认它可以选择哪些源信号

字段：

  ScopeSelector

本例：

  SignalSelectors:
    SignalRole = CAMERA_TARGET

  FrameRangeSupported = true

意义：

ScopeSelector不是最终输入清单，而是告诉GUI和Registry：

> 哪些信号有资格被展示或解析给这个Module。

未来Selector可以组合：

- Channel；
- CanId；
- MessageName；
- SignalName；
- CanonicalName；
- Unit；
- ValueKind；
- SignalRole。

为什么不硬编码0x221、0x251？

因为这些是当前车辆和DBC的Profile信息，不是Camera Target Selector在所有项目中的普遍定义。

FrameRangeSupported表示Module能否只运行指定FrameCount区间。它不表示本次实际运行范围，本次范围写入Run Manifest。


STEP M4：确认输入

字段：

  RequiredInputs
  OptionalInputs
  RequiresArtifacts


1. RequiredInputs

表示没有这些源输入端口，Module无法运行。

本例：

  PortId = camera_targets
  Role = CAMERA_TARGET
  MinCount = 1
  MaxCount = null

意义：

- 至少需要一个Camera Target输入；
- null表示契约层不限制最大数量；
- 最终由Signal Profile和用户选择解析到真实信号。


2. OptionalInputs

表示存在时可以增强结果，但缺失时不能阻断必需路径。

例如未来Camera Selector可以把以下信号列为Optional：

- Tracking State；
- Switching Flag；
- Object Type；
- Target Width。

如果某个Signal实际上不可缺少，它就不应该为了“更容易运行”而被写成Optional。


3. RequiresArtifacts

表示依赖已经治理过的上游结果，而不是直接依赖原始信号。

例子：

Residual Evidence Module通常需要：

  PrimaryOutcome Artifact
  Baseline Artifact
  Residual Artifact

它不应该自己重新读取源表，然后在内部重新定义RawError和Residual。

为什么要区分RequiredInputs与RequiresArtifacts？

因为：

  RequiredInputs   = 源信号或源端口需求
  RequiresArtifacts = Pipeline内部已经完成定义和验证的上游结果

这个区别确保同一个数学对象只由明确Stage负责。


STEP M5：确认输出

字段：

  ProvidesArtifacts
  OutputNamespace


1. ProvidesArtifacts

本例：

  ArtifactType = CANONICAL_CAMERA_TARGET
  ArtifactSchemaId = u002.canonical_camera_target
  ArtifactSchemaVersion = 0.1.0
  ExclusiveOutput = true

意义：

Module不是“增加几列”，而是承诺产生一个具有明确类型和Schema的Artifact。

ArtifactType表示工程意义。

ArtifactSchemaId和Version表示数据结构。

ExclusiveOutput = true表示在同一正式路径中最终只能存在一个被接受的Canonical Camera Target。


2. OutputNamespace

本例：

  camera.canonical_target

意义：

所有输出必须处于自己的命名空间，禁止不同Module无声覆盖同名字段。

例如：

  camera.selector_a.confidence
  camera.selector_b.confidence

在Arbitration之前，两套Resolver输出必须并存，而不是后运行的覆盖先运行的。


STEP M6：确认失败和冲突处理

字段：

  FailurePolicy
  ConflictPolicy


1. FailurePolicy

可选值：

  ABORT_RUN
  BLOCK_DEPENDENT_PATH
  SKIP_OPTIONAL_PATH

本例：

  BLOCK_DEPENDENT_PATH

意义：

Camera Target Selector失败时，依赖Canonical Camera Target的PrimaryOutcome路径必须停止；但与它无关的其他诊断路径将来仍可能继续。

规则：

- REQUIRED Module不能使用SKIP_OPTIONAL_PATH；
- OPTIONAL Module必须能够被安全跳过；
- 不能捕获异常后写一份空CSV并伪装成功。


2. ConflictPolicy

可选值：

  ERROR_ON_COLLISION
  REQUIRE_ARBITRATION
  APPEND_ONLY

本例：

  REQUIRE_ARBITRATION

现实意义：

如果Camera Resolver A和B都声称自己提供Canonical Camera Target，Engine不能选择“最后写入者”。

必须：

1. 保留两个竞争结果；
2. 由Arbitration Module读取；
3. 按明示规则选择；
4. 输出选择理由、置信度和竞争Artifact ID。


STEP M7：确认配置、代码和兼容性身份

字段：

  ConfigurationSchema
  Entrypoint
  SelfTest
  Compatibility
  ImplementationSha256
  Extensions


1. ConfigurationSchema

包含：

  SchemaId
  SchemaVersion
  RelativePath
  Sha256

意义：

Module允许哪些参数、参数类型和范围必须提前定义。

例如Camera Selector以后可能有：

- continuity weight；
- invalid-distance rules；
- confidence threshold；
- maximum missing duration。

这些不能只存在GUI控件里，也不能运行后无法还原。


2. Entrypoint

包含：

  RelativeFile
  Callable

意义：

Engine知道应该调用哪个文件中的哪个函数。

Manifest扫描阶段只读取字符串，不立即import该文件。


3. SelfTest

包含：

  Arguments
  ExpectedExitCode
  ExpectedToken

意义：

Registry可以在激活Module前检查最基本的运行能力。

SelfTest通过不表示算法正确，只表示：

- 代码能够启动；
- 基本依赖存在；
- 最小内置样例符合预期；
- 接口没有明显损坏。


4. Compatibility

包含：

  MinimumEngineVersion
  MaximumEngineVersion

意义：

旧Module不能在不兼容的新Engine中被静默加载。


5. ImplementationSha256

意义：

它是实现文件内容指纹。

两个文件即使都叫camera_target_selector.py，只要内容不同，SHA-256就不同。

SHA-256能证明身份一致，不能证明算法科学有效。


6. Extensions

用于未来带命名空间的非核心扩展。

它不是逃避正式字段和Change Control的“万能垃圾桶”。


六、Module Manifest的生命周期

一个Module正常进入U002的过程：

1. 先有Algorithm Card，明确问题、数学定义、假设和验证方法；
2. 实现Module代码和Configuration Schema；
3. 创建Module Manifest；
4. 计算实现和配置Schema的SHA-256；
5. Registry只读扫描Manifest；
6. Validator检查字段、Stage、依赖和冲突；
7. Registry运行SelfTest；
8. 用户在GUI中选择或Profile推荐该Module；
9. Engine解析真实输入和配置；
10. Run Manifest记录最终Module版本、Manifest SHA和配置SHA；
11. Module执行并产生Artifact；
12. 实验通过后，AlgorithmStatus才能通过Decision升级。


七、它不能替代什么

Module Manifest不能替代：

- Algorithm Card：为什么采用该数学方法；
- Source Code：算法如何实现；
- Configuration File：本次参数具体是多少；
- Experiment Log：真实数据验证结果；
- Decision Log：为什么批准进入正式Pipeline；
- Artifact Manifest：本次运行具体产生了什么结果；
- Run Manifest：本次完整执行发生了什么。


八、它防止的真实问题

1. Analyzer无限膨胀

没有Stage和ModuleKind时，correlation、baseline、event merge、SysID和Excel导出会不断塞进一个主程序。


2. 数学对象被重复定义

RequiresArtifacts迫使下游消费已定义的PrimaryOutcome、Baseline和Residual，而不是自己重算。


3. 输出被静默覆盖

OutputNamespace与ConflictPolicy禁止latest-writer-wins。


4. 参数无法追溯

ConfigurationSchema和ResolvedConfigSha256让每次Run能还原参数身份。


5. 探索算法伪装成正式算法

AlgorithmStatus使PROVISIONAL与FORMAL在机器记录里不同。


6. 一个坏插件拖垮程序

Registry先读Manifest、后运行隔离SelfTest，不在启动阶段盲目import全部代码。


九、动手练习

练习1：身份

在valid_module_manifest.json中找到：

  ModuleId
  ModuleVersion
  ContractVersion

用自己的话说出三个Version/Identity分别属于谁。


练习2：职责

找到Stage和ModuleKind。

回答：为什么这个Module不能直接计算Camera-Radar discrepancy？

正确方向：

它位于S1，职责是建立Canonical Camera Target；Camera-Radar比较属于后续Analysis View和PrimaryOutcome。


练习3：输入

比较RequiredInputs和RequiresArtifacts。

回答：如果未来Evidence Module需要Residual，它应该把Residual写在哪里？

正确方向：

写入RequiresArtifacts，而不是RequiredInputs。


练习4：失败

把valid_module_manifest.json复制到测试目录，把：

  FailurePolicy

改成：

  SKIP_OPTIONAL_PATH

再运行Validator。

预期：REQUIRED Module被拒绝。


练习5：架构判断

假设有人提出一个Module同时完成：

  Camera target selection
  discrepancy
  baseline
  event merge
  Excel export

回答：为什么不能为它写一个Manifest直接放入S1？

正确方向：

它跨越S1、S3、S4、S6和S7，破坏Stage所有权、替换能力和可追溯性，必须拆分。

十一、五句最终记忆

1. Module Manifest定义能力与边界，不保存运行结果。
2. Stage决定它在Pipeline中的位置，ModuleKind决定它承担的职责类型。
3. RequiredInputs管源输入，RequiresArtifacts管上游治理结果。
4. OutputNamespace与ConflictPolicy防止模块互相覆盖。
5. Manifest让Module可发现、可替换、可验证、可追溯，但算法是否正确仍由Experiment决定。

1. Product objective

Convert a large U001 accepted signal package into a small, traceable set of engineering review Candidates, then confirm them with synchronized CAN and video evidence in U003.

The first Golden use case evaluates Radar target-distance loss against reconstructed Camera target geometry. It is an explainable vertical slice used to prove the platform, not the final limit of U002 analysis capability.

2. Product boundaries

U001 - Data Foundation

- Converts source data into a traceable accepted package.
- Owns FrameCount, signal catalog, validity, age, update provenance and source lineage.
- Does not own target arbitration, residual analysis, anomaly detection or engineering conclusions.
- Portable product acceptance is complete; future high-code refactoring is deferred until the U001-U002-U003 Golden path is stable.

U002 - Analysis Workbench

- Owns qualified analytical Module selection, configuration, orchestration and evidence production.
- Preserves fixed Stage contracts while allowing qualified Modules within the correct Stage.
- Uses the accepted CLI path for Validator, Preflight and Executor; the GUI does not duplicate algorithms.
- Current development focus.

U003 - Evidence Review Workbench

- Owns synchronized video/CAN review, Candidate navigation, ReviewMemo editing and plot-data export.
- One-file portable product and U002 review handoff are accepted.
- Current feature set is frozen except for a reproducible Golden-path blocker.

3. U002 fixed Stage architecture

S0  Intake and Contract Gate
    Validate source identity, FrameCount domain, schemas and Run scope.

S1  Semantic Reconstruction
    Load candidate-signal Modules such as Camera target continuity/arbitration and Radar measurement validity.

S2  Analysis View and Population
    Build one governed analytical population while preserving source, validity, confidence and reason fields.

S3  Primary Outcome
    Define the explicit quantity, direction, units and engineering question.

S4  Baseline and Residual
    Apply a qualified baseline/residual Module when required; baseline is an analytical result, not a permanently fixed distance rule.

S5  Evidence Engines
    Produce explainable statistical, geometry, rarity, confidence or future SysID evidence.

S6  Candidate Synthesis
    Apply threshold, persistence, merge, ranking and bounded Top-N review policy.

S7  Handoff and Export
    Export Candidate inventory, ReviewMemo trace, synchronized review package and optional plot/report artifacts.

Modules may be reordered only within their assigned Stage. Cross-Stage movement is prohibited by contract.

7. Post-MVP roadmap

Priority 1 - Product stabilization

- Close reproducible GUI or handoff defects only.
- Add a stable installer/packaging boundary after the GUI Golden Run.
- Keep TEMP hygiene, failure-memory coverage and three-command operation mandatory.

Priority 2 - Analytical expansion through qualified Modules

- Camera/Radar discrepancy and conditional baseline/residual analysis.
- Feature screening suitable for mixed ADAS time-series data.
- Scenario segmentation and high-risk condition discovery.
- AR/ARX, prediction-error and residual-whiteness Modules after the static path is stable.
- Optional LDW, TSR, Resume, HMI, GNSS, LiDAR or ROS-oriented Modules as requirements become concrete.

Priority 3 - Lineage-aware iterative analysis

- Keep U001 Accepted Package as the root-source authority.
- If a later U002 Run consumes a prior U002 Artifact, introduce an explicit derived-input contract with RootU001PackageId, ParentRunId, ArtifactRole, EntryStage and transformation lineage.
- Never place a derived Artifact into the U001 input field or inherit hidden Run state.

Priority 4 - Deferred refactoring

- Rebuild U001 and U003 in the same high-code modular style only after the complete Golden path is frozen and a consumer need justifies reopening them.

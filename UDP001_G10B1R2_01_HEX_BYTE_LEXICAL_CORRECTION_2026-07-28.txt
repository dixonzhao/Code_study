UDP001 G10B1R2 - RAW CAN HEX-BYTE LEXICAL CORRECTION
Date: 2026-07-28
Status: IMPLEMENTATION CORRECTION SPECIFICATION

======================================================================
1. PURPOSE
======================================================================

Correct one proven lexical defect in the G10B1 single-pass discovery engine.

The Raw MATLAB CAN CSV stores byte cells as hexadecimal text.  Hexadecimal
digits-only text remains hexadecimal.  For example:

- "00" -> 0
- "10" -> 16, NOT decimal 10
- "7F" -> 127
- "FF" -> 255

The current decimal-only validity rule rejects values containing A-F and can
therefore reject complete CAN messages, including the authoritative FrameCount
message.

This correction does not change the accepted architecture, signal catalog,
batch plan, frame assignment policy, hold policy, output schemas or Data
Contract semantics beyond explicitly declaring the Raw-byte lexical encoding.

======================================================================
2. ACCEPTED EVIDENCE
======================================================================

G10B1D2 returned:

Interpretation:

- exactly one Channel-2 / CAN-ID-0x620 / DLC-8 source group exists;
- all eight byte cells are present on 9,998 observed message rows;
- exact DBC signal FrameCount resolves and uses four payload bytes;
- all four FrameCount bytes are present on 9,998 rows;
- decimal-only conversion accepts only 2,644 of those rows;
- Byte0 decimal acceptance is 3,909 / 9,998, closely matching the expected
  digits-only fraction of two-character hexadecimal text;
- Byte5 is present on 9,998 rows but decimal-valid on zero rows, consistent
  with a hexadecimal token containing A-F rather than a missing byte.

Decision:

- source structure and FrameCount selection are accepted;
- the decimal-only byte validity rule is rejected;
- do not perform another source-structure probe before this correction.

4. AUTHORITATIVE FRAME-KEY IDENTITY
======================================================================

Keep the exact authoritative identity:

- Channel = 2
- CAN ID = 0x620
- SignalName = FrameCount
- Canonical role = FRAME_KEY

0x620 is a CAN Message containing five DBC signals.  The other four signals

======================================================================
5. ONE CANONICAL RAW-BYTE PARSER
======================================================================

Implement one canonical scalar normalization function and one vectorized
adapter used by every message route.

Recommended semantic name:

parse_raw_can_hex_byte(value) -> int | missing | invalid

Exact rules:

1. Preserve the distinction among PRESENT, MISSING and INVALID.
2. Blank, whitespace-only and actual NaN are MISSING / NO_UPDATE inputs.
3. Trim surrounding whitespace before parsing.
4. Accept one or two hexadecimal digits [0-9A-Fa-f].
5. Optionally accept a 0x or 0X prefix followed by one or two hexadecimal
   digits, if the existing source reader can expose such values.
6. Interpret every accepted token in base 16, including digits-only tokens.
7. Return a normalized integer in [0,255].
8. Preserve 0 as a real valid byte.
9. Reject signs, decimal points, scientific notation, separators, more than
   two hexadecimal digits after an optional prefix and any non-hex character.
10. Never call decimal pd.to_numeric as the authoritative byte parser.
11. Never infer decimal versus hexadecimal per cell.
12. Do not silently coerce INVALID to MISSING or zero.

Examples:

"0"     -> 0
"00"    -> 0
"09"    -> 9
"10"    -> 16
"aF"    -> 175
"FF"    -> 255
"0x10"  -> 16
""      -> MISSING
"  "    -> MISSING
"-1"    -> INVALID
"1.0"   -> INVALID
"100"   -> INVALID
"0x100" -> INVALID
"GG"    -> INVALID

The normalized UInt8 payload produced by this parser must be the only payload
passed to Foundation.decode_physical_value or equivalent accepted Foundation
decode primitives.

======================================================================
6. APPLY THE SAME RULE TO ALL ROUTES
======================================================================

The exact same canonical parser must be used for:

- the dedicated Channel-2 / 0x620 / FrameCount route;
- every candidate message in all 23 batches;
- byte-valid masks;
- complete/invalid message classification;
- scalar fallback decode paths;
- vectorized decode paths;
- quality counters;
- runtime validation helpers that inspect Raw byte values.

There must be no separate decimal parser for FrameCount and no second parser
inside the candidate-batch path.

Message classification remains:

- all required message cells blank -> NO_UPDATE;
- some but not all message cells present -> INCOMPLETE_MESSAGE;
- all present but at least one token fails the canonical hex parser ->
  INVALID_BYTE;
- all present and every token normalizes to 0..255 -> DECODED_UPDATE.

For the observed Channel-2 / 0x620 message rows, a present token such as FF is
valid and must not cause INVALID_BYTE.

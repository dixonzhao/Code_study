UDP001 G10B1R4 - BOUNDED MULTIPROCESS ENGINE v0.4B
Date: 2026-07-28
Status: IMPLEMENTATION SPECIFICATION

======================================================================
1. PURPOSE
======================================================================

Add bounded process-based parallel decoding of changed candidate payloads to
the accepted v0.4A engine while preserving v0.4A frame data exactly.

This is a performance implementation change only.  It does not change source
semantics, FrameCount authority, signal selection, batch assignment, validity,
hold policy, output schemas or mathematical meaning.

Use ProcessPoolExecutor, not ThreadPoolExecutor.  The candidate DBC decode path
is Python CPU-bound and ordinary threads are not expected to bypass the GIL.

======================================================================
4. CLI AND WORKER POLICY
======================================================================

Add:

--workers INTEGER

Rules:

- default = 4;
- minimum = 1;
- maximum = 8;
- values outside 1..8 fail before reading the source;
- workers=1 executes the accepted v0.4A decode semantics without creating a
  process pool;
- quality JSON, manifest and capsule record the effective worker count;
- GUI integration is deferred until v0.4B is accepted.

Use:

from concurrent.futures import ProcessPoolExecutor

Ensure Windows spawn and later PyInstaller compatibility:

- every worker function is module-level;
- no lambda, nested worker, closure or bound GUI method is submitted;
- call multiprocessing.freeze_support() under the normal main guard;
- protect program launch with if __name__ == "__main__";
- worker arguments and return values are explicitly pickleable;
- do not pickle dynamically imported Foundation module objects;
- do not create a process pool during module import or self-test discovery.

======================================================================
5. OWNERSHIP BOUNDARY
======================================================================

MAIN PROCESS OWNS EXCLUSIVELY:

- opening and reading CANDump.csv;
- exact encoding/delimiter/header handling;
- globally monotonic SourceRowIndex;
- Raw source scan count = 1;
- hexadecimal payload normalization;
- first/change/reuse detection and cross-chunk payload cache;
- exact Channel-2 / 0x620 / FrameCount decode;
- authoritative FrameCount state machine;
- frame assignment;
- frame finalization;
- deterministic merge ordering;
- all final CSV/JSON/manifest/capsule writes;
- output validator;
- failure cleanup and final exit code.

WORKER PROCESSES MAY ONLY:

- receive changed candidate payload records selected by the main process;
- decode configured non-Frame-key candidate signals for assigned message-plan
  partitions;
- return compact decoded records plus bounded worker counters/errors.

WORKERS MUST NOT:

- open or reread CANDump.csv;
- open DBC files per task;
- write final output files;
- decode or modify FrameCount;
- own frame state;
- decide signal eligibility, BatchId or validity policy;
- perform forward fill or hold;
- create nested process pools;
- swallow exceptions;
- return C-0 independently.

======================================================================
6. WORKER INITIALIZATION
======================================================================

Create one persistent ProcessPoolExecutor outside the pandas source-chunk loop.

Use a module-level worker initializer to load once per worker:

- accepted Foundation path/module;
- plain serializable candidate message plans;
- plain serializable DBC signal definitions required by that worker;
- exact canonical hexadecimal byte semantics;
- immutable BatchId/signal ordinals.

Do not pass dynamically imported Python module objects through pickle.

Convert every worker plan to plain built-in structures or a module-level
pickleable dataclass containing only strings, integers, floats, booleans,
tuples and lists.

The Frame-key plan is excluded from every worker registry.

======================================================================
7. DETERMINISTIC PARTITIONING
======================================================================

Before source reading, partition the 69 candidate message plans into exactly W
deterministic worker partitions, where W is the effective worker count.

Recommended deterministic balancing weight:

configured signal count per message plan.

Algorithm:

1. sort message plans by descending signal count, then MessagePlanOrdinal;
2. assign each plan to the currently lowest total-weight partition;
3. break ties by lower partition ordinal;
4. within each partition, restore MessagePlanOrdinal order.

Record only counts/ordinals, not Raw values, in quality metadata.

The same input, config and W must always produce the same partition plan.

======================================================================
8. BOUNDED CHUNK EXECUTION
======================================================================

For each pandas source chunk:

1. main process reads the chunk once;
2. main process normalizes payloads and detects first/change/reuse exactly as
   v0.4A;
3. main process handles the Frame-key route serially;
4. main process builds at most one compact task per worker partition containing
   changed candidate payload records only;
5. submit at most W tasks for that chunk;
6. do not read the next source chunk while more than one chunk is in flight;
7. wait for all W partition tasks;
8. propagate any worker exception as a blocking run failure;
9. merge results and stable-sort by:
   SourceRowIndex,
   MessagePlanOrdinal,
   SignalOrdinal,
   CanonicalName;
10. replay the accepted v0.4A serial cache/frame logic in the main process;
11. finalize/write frames only in the main process;
12. then release the chunk buffers and continue.

Do not submit one Future per signal.
Do not submit one Future per source row.
Do not queue all source chunks at once.

Worker return data should be compact tuples/arrays, not nested dictionaries per
scalar when a compact deterministic representation is possible.

======================================================================

- B=23;
- M=69;
- S=10000;
- U=1578619;
- F=2062;
- Q=23;
- H0/X0;
- P=189341;
- Z=500511;
- identical frame sequence in every batch;
- identical candidate RawCode/PhysicalValue/current validity per frame;
- identical deterministic batch frame-shard CSV bytes.

Only runtime/parallel metadata may differ:

- program version;
- worker count;
- elapsed time;
- worker partition statistics;
- file hashes of metadata files containing those approved differences.

Do not weaken or normalize differences in frame data.

======================================================================
12. FAILURE RULES
======================================================================

Any worker exception:

- cancels outstanding tasks where possible;
- shuts down the executor;
- prevents C-0;
- prevents validator PASS;
- writes the accepted bounded error/traceback artifact;
- exits nonzero.

Do not silently retry a failed partition in the main process.
Do not fall back from workers=4 to workers=1 without explicit user command.
Do not emit partial success.

Preserve --debug-traceback.

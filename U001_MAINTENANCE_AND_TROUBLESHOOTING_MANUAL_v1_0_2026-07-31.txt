======================================================================
0. 维护原则
======================================================================

U001 已完成并冻结。维护不是继续增加功能。

允许重开：

1. 可复现的 U001 defect；
2. U002 证明存在 Data Contract compatibility blocker；
3. 经批准的 semantic-preserving performance change。

不允许直接重开：

- 想把 analyzer 塞进 U001；
- 想把 Camera 1/3 stitching 塞进 U001；
- 想“顺便”改 baseline、event、SysID；
- 仅为了清理 Gate 名称或美化代码；
- 没有 reference fixture 和 equivalence evidence 的性能重写。

每个故障先归属一个责任层：

1. Data Semantic
2. Algorithm
3. Program
4. Orchestration
5. Runtime
6. Packaging
7. Human Review

只修一个 owner layer。不能通过改 validator 掩盖 product difference，也不能用改
算法掩盖 runtime/packaging 问题。

2. 12 个正式程序及职责
======================================================================

P01 u001_foundation_core_v0_1.py
职责：
- 探测 CSV encoding/delimiter/header；
- 解析 DBC；
- 识别 IDxxx_channel_8_byte groups；
- 验证 8 bytes 完整性；
- 建立 source-present/DBC-matched signal catalog。
不负责：相关性、筛选统计、FrameCount view。
self-test 意义：纯合成输入检查 CSV/DBC/parser/decode foundation 的确定性逻辑。

P02 u001_selected_update_decoder_v0_1.py
职责：
- 按 approved selection 解码真实 signal updates；
- 保留 source order、raw code、physical value 和 decode status；
- 输出 update-domain long form。
不负责：zero fill、无限 forward fill、FrameCount aggregation。
self-test 意义：验证 endian/signedness/scale/offset、selection 和 update row schema，
不证明真实 DBC 业务定义正确。

P03 u001_framecount_assignment_v0_1.py
职责：
- 使用 CH2/0x620/FrameCount 将 source updates 分配到视频 frame domain；
- 记录 assignment status 和 assignment age rows；
- 拒绝不受控的无限 frame label propagation。
不负责：measurement hold。
self-test 意义：验证 monotonicity、assignment limit、unassigned 状态和 schema。

P04 u001_semantic_validity_classifier_v0_1.py
职责：
- 应用 ValueKind、SignalRole、ValidityRule；
- 区分 true zero/false、missing、invalid default、unknown enum；
- 保留 MissingReason。
不负责：统计异常或 root cause。
self-test 意义：验证 mixed dtype、validity rule、controlled MissingReason，不证明每个
公司 signal 的人工 policy 已正确配置。

P05 u001_framecount_view_builder_v0_1.py
职责：
- 构建一行一个 canonical FrameCount；
- 应用 approved within-frame policy；
- 输出 value/label/updated/update_count/age/valid/missing_reason group。
不负责：cross-frame unbounded hold、mean/median/interpolation。
self-test 意义：验证 duplicate update aggregation、frame ordering、group schema 和 gaps。

P06 u001_signal_cadence_bounded_hold_v0_1.py
职责：
- 估计/记录 cadence quality；
- 按 explicit HoldPolicy/MaxAgeFrames 做 bounded hold；
- 保存 S__age 和 VALID_CARRIED / STALE。
不负责：为所有 signal 自动 forward fill。
self-test 意义：验证 NONE/HOLD_LAST_BOUNDED、age boundary、event flag 不保持等规则。

P07 u001_output_package_assembler_v0_3.py
职责：
- 把上游 accepted artifacts 组装成标准六文件包；
- 生成 catalog/quality/manifest/review view；
- 验证 dynamic row counts 和 identity。
不负责：生成新的数据语义。
self-test 意义：验证六文件 schema、hash/count linkage、dynamic row-count consistency；
不证明上游物理值正确。

P08 u001_g8a_thin_orchestrator_v0_5.py
职责：
- Controlled Profile legacy path 的薄调度；
- 按批准顺序调用 P01-P07；
- 保持命令、路径和失败边界。
不负责：实现各 stage 的数据逻辑。
self-test 意义：验证 command planning、stage order、token/failure propagation；不运行
真实 full source。

P09 u001_auto_discovery_profile_builder_v0_2.py
职责：
- 从 G1 catalog 自动建立 technically eligible signal inventory；
- 生成 provisional profile、batch map 和 control files；
- 固定 FrameCount signal 选择。
不负责：判断与 outcome 的相关性。
self-test 意义：验证 eligible/excluded count invariants、fixed frame key、batch/profile
schema 和 deterministic ordering。

P10 u001_g10b_single_pass_discovery_engine_v0_5a.py
职责：
- 对大量 eligible signals 做 bounded-memory single-pass discovery；
- 生成 change-driven/update payload 和 bounded-width FrameCount shards；
- 记录 resource/quality evidence；
- 避免 700-signal monolithic table。
不负责：U002 statistical ranking。
self-test 意义：验证 bounded buffers、snapshot/frame semantics、shard identities、abort
evidence 和 deterministic assembly；不等于 full-scale performance test。

P11 u001_discovery_controller_v0_2.py
职责：
- 实现 public headless request/response interface；
- make request、preflight、run、validate；
- child process/evidence ownership；
- incomplete staging 和 final promotion；
- 只在完整验证后 ReadyForU002=1。
不负责：GUI layout 或内部算法。
self-test 意义：验证 request schema、path/fingerprint rules、child plan、failure categories、
atomic response construction 和 synthetic end-to-end state machine。

P12 u001_data_preparation_workbench_gui_v0_4a.py
职责：
- 人类操作界面；
- AUTO_DISCOVERY / Controlled Profile / New Case；
- Controller-only 调用；
- Execute New Run 五阶段顺序、日志、取消和打开输出。
不负责：数据处理逻辑。
self-test 意义：验证 UI contract、fields/defaults/actions、widget registry、Controller-only
boundary 和 failure-stop sequence；不等于真实 GUI 可见性测试。

4. 程序调用顺序
======================================================================

4.1 用户调用链

  U001_Workbench.exe
  -> Runtime Host v0.6
  -> GUI v0.4a
  -> Controller v0.2

4.2 AUTO_DISCOVERY controller 链

  Controller Self-test
  -> Create Request
  -> Preflight
  -> Run Request
  -> Validate Response

Run Request 内部概念顺序：

  C1 Foundation Catalog
  -> C2 Auto Profile Build
  -> C3 Profile Validation
  -> C4 Single-pass Discovery Run
  -> C5 Discovery Result Validation
  -> C6 Response Construction/Validation

Discovery 内部数据顺序：

  Catalog
  -> Selected Update Decode
  -> FrameCount Assignment
  -> Semantic Validity
  -> Frame View
  -> Cadence/Bounded Hold
  -> Package/Shard Assembly

4.3 为什么层次较多

这是为了区分：

- 数据语义是否正确；
- 单程序是否正确；
- 调度是否正确；
- 打包 runtime 是否能运行；
- 用户双击入口是否可用。

历史开发 Gate 名称不是用户概念。维护时保留程序责任和测试层，不再把每个小修复
扩张成新的产品层。

6. 变更流程
======================================================================

6.1 提交 defect 前

记录：

- accepted baseline version/SHA；
- smallest reproducible input；
- exact command/GUI action；
- previous passing boundary；
- first failing boundary；
- expected vs observed；
- C-7 category；
- stdout/stderr/abort evidence location；
- 是否影响 Data Contract。

6.2 允许的修改方式

1. 从 frozen baseline 复制新版本；
2. 不覆盖旧文件名；
3. PROGRAM_NAME / PROGRAM_VERSION / token 一致升级；
4. 只修改 owner layer；
5. 新增一个能捕获该 failure 的 self-test；
6. 运行该 program source self-test；
7. 运行 independent conformance；
8. 10k real integration；
9. 与 frozen reference 做 semantic comparison；
10. 必要时 full-source；
11. 重新构建 portable；
12. 运行 final acceptance 和 visible GUI；
13. 记录 Decision Log / node report / downstream compatibility。

6.3 什么算 Data Contract change

以下任一变化必须显式升 contract/schema 或记录 compatibility decision：

- 字段新增/删除/改名/改义；
- FrameCount ownership 或 assignment 改变；
- MissingReason vocabulary 改变；
- ValueKind/SignalRole/Unit 改变；
- aggregation/hold 语义改变；
- 六文件身份/关系改变；
- request/response schema 改变；
- manifest/hash/cache rules 改变。

只提高读取速度但 bytes/semantics 等价，不应修改 contract。

7. 常见故障矩阵
======================================================================

7.1 PROGRAM_NOT_APPROVED

症状：Host 拒绝运行某 source program。
Owner：Runtime/Inventory。
检查：
- 文件名是否 exact 12 inventory；
- 是否把新版本放进 release 但未更新 manifest/host/builder；
- 是否从错误目录调用；
- SHA/version 是否匹配。
禁止：关闭 approved-program 检查。

7.2 ModuleNotFoundError: pandas

Owner：Packaging/Runtime collection。
原因：developer venv 有 pandas，但 copied/frozen runtime 未包含。
处理：
- 使用 intended build environment；
- 检查 explicit import/hidden import；
- 在 packaged runtime 中跑 hosted self-tests；
- 不要在 venv 内使用 pip --user；
- 不要临时复制 site-packages 作为正式修复。

7.3 cannot import name filedialog from tkinter

Owner：Packaging。
原因：freezer 未收集 Tkinter submodule。
处理：
- builder/host 显式收集 filedialog、messagebox、ttk 等实际依赖；
- 重新 build；
- visible GUI smoke 打开 file dialog；
- source self-test PASS 不足。

7.4 failed to extract pandas/test/... 或 package 过大

Owner：Packaging collection scope。
原因：错误 collect-all，把 tests/docs/benchmarks 收入 package，或 onefile TEMP 提取
受限。
处理：
- 使用 onedir/windowed；
- exclude tests/docs/benchmarks；
- 只 collect runtime-required modules；
- 验证 manifest file count/size；
- 保持整个 folder，不单独移动 EXE。

7.5 PermissionError / endpoint security / file lock

Owner：Publication/Filesystem。
处理：
- 使用 verified copy2 + bounded retry；
- destination 必须不存在；
- build 先在 unique 04_TEMP staging 完成；
- 失败保留 incomplete marker；
- 不用大目录 move/rename 反复试；
- 不删除 accepted release。

7.6 Run ID/output already exists

Owner：Orchestration/User input。
行为：正确的 no-overwrite protection。
处理：创建新 Run ID；归档旧 run。不要改程序允许覆盖。

7.7 FRAME_DOMAIN_EMPTY_OR_INCONSISTENT

Owner：Data Semantic/Profile/Frame Assignment。
检查：
- 0x620 下明确选择 Signal=FrameCount，而不是 message 内其他 4 个 signal；
- Channel=2；
- DBC2 对应正确；
- header bytes 完整；
- FrameCount numeric/monotonic；
- selected source region 是否包含 frame updates；
- assignment age limit 是否导致全部 unassigned。

7.8 update row count 与预期不一致

Owner：Package/Count invariant 或 source scope。
检查：
- 不要假设 raw source row count = decoded signal update row count；
- 一条 CAN message 可产生多个 signal updates；
- MaxSourceRows 与 full source scope；
- package assembler 必须使用动态实际 row count；
- manifest/quality/file row counts 必须互相验证。

7.9 AttributeError: list has no attribute setdefault

Owner：Program implementation/schema container type。
处理：
- 用最小 fixture 复现；
- 明确 list/dict contract；
- 修 program，不改 validator；
- 新增类型契约 self-test；
- rerun 10k and semantic compare。

7.10 持续内存增长

Owner：Discovery engine live data structure。
处理：
- 立即停止，保留 abort/resource evidence；
- 不等到系统耗尽；
- 记录 peak RSS 和 source rows；
- 检查 monolithic DataFrame、unbounded dictionary/list、snapshot accumulation；
- 使用 streaming/chunking/bounded buffers/shards；
- memory cap 本身不是性能修复；
- 10k -> 40k -> full 逐级验证。

7.11 多 worker 但只有一个 CPU 忙

Owner：Performance architecture。
可能原因：serial reader、GIL、单一 queue bottleneck 或 workers 等待同一 input。
处理：先 profile；按 independent shards 并行；冻结 serial reference；证明输出语义等价。
禁止：为提高 CPU 百分比复制多份 800MB source 而无 I/O/semantic design。

7.12 CHILD_EVIDENCE / CHILD_ARTIFACT / CHILD_TOKEN

Owner：Controller child boundary。
检查：
- stage output ownership；
- stdout/stderr 是否存在；
- child exit code；
- artifact path 和 completion token；
- child 是否写到 controller 已占用的目录；
- run 是否来自 accepted child version。
不要让 controller 伪造 child evidence。

7.13 Manifest 不一致

Owner：Identity/Packaging/Run mutation。
检查：
- stable version/SHA provenance；
- 不要仅因为 manifest 未重复 literal source filename 就拒绝；
- 但 source/DBC/control/artifact hash 必须一致；
- 输出是否被手工编辑；
- response/package 是否来自不同 Run ID。
禁止：扩大 normalization whitelist 掩盖未知差异。

7.14 ZIP 中缺少 03_CASES

Owner：Packaging artifact semantics。
原因：普通 ZIP 创建常省略 empty directory。
处理：
- folder side 和 ZIP side 分开验证；
- builder 应原生创建 directory entry；
- 若 final build 仅此一项失败，允许经授权的 narrow audited repair：先备份，记录
  before/after hashes，只增加 exact empty entry，再跑完整 independent acceptance；
- 不把“unpacked 有目录”当成 ZIP 也有。

7.15 有 CSV 但没有 ReadyForU002

Owner：Run completeness。
处理：整次运行 C-7，U002 禁止消费；保留 incomplete evidence，重新定位 first failing
boundary。

7.16 信号值不合理但所有 tests PASS

Owner：可能是 Data Semantic / DBC / Business definition。
说明：self-tests 证明程序按定义执行，不证明 DBC 或 signal meaning 正确。
检查：
- DBC Channel assignment；
- scale/offset/unit；
- invalid default；
- ReferencePoint/coordinate definition；
- 视频/工程知识；
- signal policy 是否仍 provisional。

======================================================================
8. 故障证据和回传格式
======================================================================

成功：只需一行。

  <TEST_OR_RUN>-PASS ... C-0

失败：

  <TEST_OR_RUN>-FAIL L-<OwnerLayer> A-<Artifact> E-<ErrorCode> C-7
  MEMO1-<short fact>
  MEMO2-<short fact>
  MEMO3-<short fact>

最多三条短 memo。长 stdout/stderr/hash 放文件或 GitHub transfer，不让人手抄。

必须保存：

- exact command；
- stdout；
- stderr；
- abort/incomplete marker；
- request/preflight/response manifest；
- source/program/version/hash identity；
- first failing stage。

  python .\UDP001\04_TEMP\u001_final_release_acceptance_v0_2.py --release-root .\UDP001\04_TEMP\U001_FINAL_RELEASE_NEW

必须：

10. 性能修改规则
======================================================================

U001 v0.2 已接受正确性、可追溯性和 bounded memory 优先于速度。

性能优化前必须：

1. profile 并证明真实 bottleneck；
2. 固定 reference fixture 和 expected outputs；
3. 记录 elapsed/RSS/rows/CPU/I/O；
4. 只改 performance owner layer；
5. serial implementation 作为 oracle；
6. 比较 output hash 或逐字段 semantic equality；
7. 验证 deterministic ordering；
8. 10k/40k/full progressively；
9. Data Contract 不变；
10. 如不能证明等价，不允许替代 baseline。

可能的后续方向：按 independent shard 做 bounded parallelism、减少重复 parse、使用
新 serialization profile（Parquet/Arrow）。这些是未来 proposal，不是当前 U001
正式能力。

======================================================================
11. 维护者应该知道的几个关键区别
======================================================================

11.1 Frame assignment vs measurement hold

Frame assignment：把后续 source rows 标上最近可信 FrameCount，是同步 metadata。

Measurement hold：把一个 signal 的旧 physical value 带到后续 frames，是数据 view
policy。两者 age 字段、语义和限制不同，不能合并。

11.2 Update stream vs Frame View

D1 是真实 update event 长表；D2 是 frame aggregation/hold 后分析 view。D2 不能替代
D1 的 sub-frame provenance，D1 也不能直接当 20 Hz regular time series。

11.3 Valid zero vs missing

Boolean false、速度 0、enum code 0 可以是真值。只有 signal-specific validity rule 才
能判 invalid。全局 blank-to-zero 被禁止。

11.4 Discovery eligibility vs relevance

U001 选择 technically eligible = source present + DBC matched + decodable。它不代表
与 discrepancy 有关。相关性筛查属于 U002。

11.5 Self-test vs acceptance

Self-test 证明局部 contract；integration 证明真实 Case 路径；packaged hosted tests
证明 frozen runtime；visible smoke 证明用户入口；final acceptance 才证明 product。
